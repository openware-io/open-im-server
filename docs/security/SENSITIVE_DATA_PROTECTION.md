# 敏感数据保护与脱敏设计

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 状态 | Proposed |
| 适用范围 | `gateway`、各领域服务、`im-access-ws`、MySQL、MongoDB、Redis、RocketMQ、备份与管理后台 |
| 目标版本 | 分阶段交付，不要求一次性迁移全部历史数据 |
| 责任方 | 平台基础设施、安全、用户域、消息域、管理域 |

## 2. 背景与目标

当前系统以 MySQL 作为权威业务存储，MongoDB 保存热消息投影，Redis 承担在线状态、缓存和跨实例协同，RocketMQ 承担命令与事件持久化。聊天正文、用户 PII（手机号、邮箱）和设备推送令牌可能跨越多个节点。

本设计采用服务端的**应用层信封加密**。数据库磁盘加密、Kubernetes Secret、传输 TLS 是必要的基础保护，但不能代替应用层字段加密：拥有数据库导出、备份或运行时存储读取权限的主体不得直接得到明文。

### 2.1 安全目标

1. 密码、令牌、聊天内容与 PII 不以明文落入 MySQL、MongoDB、Redis、RocketMQ、备份、日志和监控系统。
2. 解密仅发生在具备业务授权、明确读取用途的服务调用中，且默认展示脱敏结果。
3. 密钥与密文分离；应用配置、镜像、源码仓库和业务数据库中不保存主密钥。
4. 支持按密钥版本轮换、历史数据渐进迁移、灰度和回滚。
5. 保留必要的查询、分页、排序、去重、TTL 与消息投递能力，不对所有字段进行无差别加密。

### 2.2 非目标

1. 本期不实现默认端到端加密（E2EE）。E2EE 与平台审核、举报取证、跨端历史同步和服务端检索存在产品取舍，应作为私密会话的独立能力评审。
2. 本期不把数据库 TDE 作为唯一方案；TDE 仍应在生产环境启用。
3. 不允许以可逆加密替代密码哈希。

## 3. 数据分类与处理规则

| 等级 | 示例 | 存储要求 | 默认展示 | 日志与导出 |
| --- | --- | --- | --- | --- |
| S4 极高敏感 | 密码、JWT/刷新令牌、推送 Token、KMS 凭据 | 密码使用不可逆哈希；其余字段使用应用层加密 | 永不展示原值 | 严禁记录；导出仅允许指纹或状态 |
| S3 高敏感 | 聊天正文、图片/文件私有地址、手机号、邮箱、身份资料、举报原文 | AES-256-GCM 字段/载荷加密 | 脱敏；按授权临时解密 | 严禁明文；审计只保存标识与摘要 |
| S2 内部敏感 | 昵称、签名、群公告、订单联系人、管理备注 | 按字段风险决定加密，生产备份必须加密 | 业务角色可见或局部脱敏 | 结构化日志最小化记录 |
| S1 内部 | 用户 ID、会话 ID、消息序号、状态、时间、类型 | 保留最小明文用于索引和路由 | 可按权限展示 | 可记录必要元数据 |

### 3.1 密码规则

- `user.password` 仅存密码哈希。现有 BCrypt 可继续使用；新建或成功登录后的密码可按配置逐步迁移至 Argon2id。
- 密码、密码哈希、重置验证码均不得返回 API 响应、日志、异常消息或审计详情。
- 密码验证使用恒定时间的框架实现；失败信息不得区分“用户不存在”和“密码错误”。

## 4. 总体架构

```text
业务服务 / 网关 / WebSocket
        │  认证、租户、数据用途
        ▼
Sensitive Data SDK
  ├─ PolicyEnforcer：是否允许读取原文
  ├─ EnvelopeCrypto：加密、解密、密钥版本处理
  ├─ Masker：按角色与场景脱敏
  ├─ SearchToken：HMAC 检索令牌
  └─ AuditPublisher：只记录元数据的审计事件
        │
        ▼
KMS 或 Vault Transit
  └─ KEK 管理、DEK 包装/解包、轮换、访问策略
        │
        ▼
MySQL / MongoDB / Redis / RocketMQ / 备份
  └─ 密文、nonce、认证标签、keyVersion、最小检索元数据
```

### 4.1 密钥层级

- `KEK`：仅由 KMS/Vault 保存，按环境、租户域和数据域隔离，例如 `prod/im/message-content`、`prod/im/user-pii`。应用不能读取 KEK 原文。
- `DEK`：数据加密密钥。第一阶段按“租户 + 数据域 + 月份”生成，降低 KMS 调用与密钥元数据量；高价值租户或高风险字段可升级为每记录 DEK。
- `keyVersion`：密文必须保存版本。读路径支持当前和历史版本；写路径只使用当前版本。
- 缓存：服务仅可短期缓存已解包 DEK，TTL 不超过 15 分钟；不得写磁盘，不得跨进程共享。

### 4.2 加密信封格式

逻辑格式如下，实际存储可拆分为多个列或 JSON 字段：

```text
enc:v1:<keyVersion>:<base64(nonce)>:<base64(ciphertext-and-tag)>
```

- 算法固定为 `AES-256-GCM`，随机 96-bit `nonce`，禁止 nonce 重用。
- 使用 AAD 绑定 `environment|tenantId|dataType|recordId|fieldName`，防止密文被复制到其他记录或字段后仍可解密。
- 加密前使用 UTF-8；JSON 使用稳定序列化。密文长度与空值应有明确的 DTO/数据库约定。
- 认证失败、版本未知、KMS 不可用均视为安全失败，不得退回明文读取。

## 5. 当前数据面改造矩阵

| 领域 | 现有载体 | 字段/载荷 | 改造后 | 查询与索引 |
| --- | --- | --- | --- | --- |
| 用户 | MySQL `user` | `email`、`phone`、`signature` | 新增 `*_enc` 与 `*_search_token`；回填后切换读写 | 手机、邮箱精确查询使用 HMAC 检索令牌 |
| 用户 | MySQL `user_device_token` | `token` | `token_enc` + `token_fingerprint`；唯一键改为 `push_provider, token_fingerprint` | 指纹用于去重与管理端展示 |
| 消息 | MySQL 权威消息表 | `content`、`at_users_json`、媒体私有定位符 | `content_enc`、`at_users_enc`；消息 ID、会话、序号、类型保留明文 | 会话/序号索引不变 |
| 消息 | MySQL `msg_outbox` | `payload_json` | 事件中的 S3 字段使用加密子载荷 | 事件 ID、主题、分片键保持明文 |
| 消息 | MongoDB `msg_hot_message` | `content`、`atUsersJson` | `contentEnc`、`atUsersEnc`；保留 `conversationId`、`seq`、TTL 字段 | 复合索引和 TTL 索引不变 |
| 缓存 | Redis | Token、用户资料缓存、消息片段 | value 使用相同信封格式；Redis key 只含内部 ID | TTL、计数、分布式锁可保持明文 |
| 管理 | 管理库快照/举报 | 内容快照、手机号、邮箱、处理备注 | S3 字段加密，列表接口默认掩码 | 管理检索使用 ID、状态、时间与 HMAC 令牌 |
| 消息队列 | RocketMQ | `MessageSendCommand`、`MessageStoredEvent` 中正文 | 正文改为加密子载荷，消费者按用途解密 | Topic、key、sharding key 不含明文敏感数据 |

`*_search_token = HMAC-SHA-256(searchKey, normalizedValue)`。`searchKey` 与加密 KEK 分域管理；规范化规则（手机号去空格、邮箱小写化等）必须版本化。禁止用确定性加密代替检索令牌，避免扩大明文等值泄漏。

## 6. 读写与展示流程

### 6.1 写入

1. API/命令入口完成身份、租户、字段合法性校验；请求日志过滤器先行移除 S3/S4 字段。
2. 领域服务为字段构造 AAD 并调用 `SensitiveDataWriter` 加密。
3. 权威库、投影、缓存、Outbox 和 RocketMQ 仅接收密文载荷。
4. 审计记录“写入了何类敏感数据”，不记录字段原值和密文全文。

### 6.2 普通读取

1. 服务依据会话成员关系或资源归属进行授权。
2. `PolicyEnforcer` 校验用途为 `CHAT_PARTICIPANT_READ`、`PROFILE_SELF_READ` 等允许用途。
3. 通过 KMS 解包 DEK 后解密，结果仅存在于当前请求作用域。
4. 返回给资源主体的 DTO 可包含原文；响应完成后不得写入缓存或日志。

### 6.3 管理、客服与审核读取

1. 列表和常规详情接口只调用 `Masker`，不触发解密，例如手机号显示 `138****1234`，文本显示长度受限的局部掩码。
2. “查看原文”必须携带工单号/举报 ID、读取理由和短时授权；策略要求具体权限，如 `sensitive.message.unmask`。
3. 成功解密前后均写入审计事件；可配置双人审批、单次展示时长、水印和导出禁用。
4. 无权、审批失效或审计系统不可用时，返回掩码或拒绝，不返回原文。

## 7. 服务权限模型

| 服务 | 可写入 | 可解密 | 禁止解密 |
| --- | --- | --- | --- |
| `im-user-service` | 用户 PII、设备 Token | 本人资料、登录/推送必要字段 | 聊天正文、管理快照 |
| `im-message-service` | 消息正文、消息事件 | 消息写入、历史查询、撤回处理 | 无关用户 PII |
| `im-access-ws` | 无权威持久化写入 | 仅为向已授权会话投递消息 | 历史批量导出、用户 PII |
| `im-admin-service` | 举报、处理备注、管理快照 | 默认不解密；仅审批后的审核用途 | 密码、推送 Token、认证令牌 |
| `gateway` | 不持久化敏感字段 | 默认不解密 | 所有业务数据原文 |
| 异步任务/报表 | 最小必要聚合数据 | 仅经审批的批处理用途 | 原文全量导出 |

Kubernetes 中每个服务使用独立 ServiceAccount，通过工作负载身份取得 KMS 的最小权限。不得将所有服务绑定到同一个 KMS 管理员角色。

## 8. 基础设施与运维要求

1. **传输与静态保护**：客户端至网关使用 TLS；服务间 mTLS 或等价身份认证；MySQL/Mongo/Redis/RocketMQ 启用 TLS；云盘、快照、对象存储与备份启用服务端加密。
2. **网络隔离**：数据库、Redis、Mongo、RocketMQ 不暴露公网；NetworkPolicy 仅允许对应业务服务访问。
3. **凭据治理**：数据库密码、JWT 签名密钥和第三方 Token 来自 Secret Manager；Kubernetes 仅注入短期凭据引用，不提交真实值。
4. **日志治理**：增加 Logback/JSON 日志脱敏器、HTTP 请求响应脱敏器、异常拦截器和 MQ 载荷日志禁止项。禁止 `toString()` 输出 DTO 原文。
5. **备份与恢复**：备份密文与生产密钥权限隔离；恢复演练同时验证历史 `keyVersion` 可读；删除数据时同时删除投影、缓存和密钥引用。
6. **监控告警**：对 KMS 拒绝、认证失败、异常高频解密、管理员查看原文、旧密钥读写、明文格式探测建立告警。

## 9. 分阶段实施

### Phase 0：盘点与基线（1–2 周）

- 形成字段级数据资产清单，标明来源、存储、消费者、保留期、等级和 owner。
- 在 CI 增加敏感字串扫描与日志规则，先阻断密码、Token、正文出现在日志。
- 生产环境启用存储 TLS、备份加密、网络策略、独立数据库账号与 Secret Manager。
- 验收：抽检应用日志、MQ 日志、错误链路和备份策略，无 S3/S4 明文。

### Phase 1：平台能力与 PII（2–4 周）

- 在 `sdk/infrastructure` 实现 `SensitiveData` SDK、KMS 客户端、`Masker`、`PolicyEnforcer`、审计事件模型与测试替身。
- 先迁移手机号、邮箱、设备 Token、管理配置密钥；新旧字段双写，读路径优先读密文，保留短期旧字段回退开关。
- 验收：加密/篡改/AAD 绑定/轮换/脱敏/审计单元测试；不授权用户不能读原文。

### Phase 2：消息全链路（3–5 周）

- 定义加密消息事件契约，替换 `MessageSendCommand`、`MessageStoredEvent` 中的明文正文载荷。
- MySQL 权威消息、Outbox、Mongo 热投影、Redis 中的消息片段同步切换为密文。
- `im-access-ws` 仅在确认收件人会话已授权后解密并投递，禁止将解密结果写回 Redis。
- 验收：数据库/Mongo/RocketMQ/Redis 导出均检索不到测试明文；参与者仍可正常收发、拉取、撤回消息。

### Phase 3：运营治理与轮换（持续）

- 接入工单/审批、原文查看水印、审计检索与告警；制定密钥轮换与应急吊销 Runbook。
- 新写入立即使用当前 `keyVersion`；旧记录采用读时重加密和低峰批处理重加密，不停机全量改写。
- 验收：季度恢复演练、轮换演练、权限回收演练均通过。

## 10. 数据迁移与回滚规范

1. 使用新的 Flyway 脚本新增密文字段、检索令牌和 `key_version`，禁止修改已发布迁移。
2. 发布顺序：先部署兼容读写代码，再开双写，再低速回填，再以监控确认覆盖率，最后切换读路径；旧列至少保留一个发布周期。
3. 回填任务按主键分片、可重入、限流，记录已处理范围；不得将明文写入任务日志、临时文件或消息队列。
4. 回滚仅关闭“优先读密文”与“双写”开关，不删除密文字段或已生成密文；密钥吊销前必须确认没有对应版本的未迁移数据。
5. 旧明文字段的删除必须经过数据 owner、安全评审、备份生命周期确认和变更审批。

## 11. 验收指标

| 维度 | 验收标准 |
| --- | --- |
| 存储 | S3/S4 测试样本不以明文出现在 MySQL、MongoDB、Redis、RocketMQ 和备份 |
| 访问 | 未授权管理接口只能得到掩码；无工单/理由的原文读取被拒绝 |
| 密钥 | 主密钥不出 KMS/Vault；服务权限按数据域最小化；支持当前与上一版本读取 |
| 完整性 | 篡改 nonce、AAD、密文或 keyVersion 时解密失败且不泄露原文 |
| 业务 | 消息收发、离线拉取、未读计数、撤回、设备推送、手机号/邮箱精确查询保持正确 |
| 可观测性 | 每次原文解密均有审计；日志、异常、指标标签无 S3/S4 原文 |
| 性能 | P99 解密延迟、KMS 错误率、DEK 缓存命中率有基线并设告警阈值 |

## 12. 后续决策项

1. 生产环境优先选择云 KMS 还是 HashiCorp Vault Transit，并明确跨地域容灾方案。
2. 多租户正式上线前，确认 `tenantId` 的来源、隔离模型以及是否采用每租户 KEK。
3. 明确内容审核的合规边界、原文查看审批人、审计保留期与用户数据删除策略。
4. 对私密会话是否提供可选 E2EE 进行单独的产品与安全评审。
