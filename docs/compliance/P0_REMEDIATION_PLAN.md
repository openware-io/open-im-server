# IM 系统 P0 合规问题整改方案

> 状态：方案初版（待评审后执行）
> 关联：docs/compliance/CHINA_COMPLIANCE.md（清单与总纲）
> P0 定义：法律红线，须立即启动、限期闭环。共 6 项。

---

## P0-1 资质办理（ICP/EDI/App 备案/等保）

### 目标
补齐市场准入资质，避免无证经营导致下架、关停或处罚。

### 现状与差距
全部待确认：ICP 备案/许可证、EDI、App 备案、等保定级备案均未见材料。

### 方案
| 步骤 | 动作 | 责任方 | 周期 |
| --- | --- | --- | --- |
| 1 | 确定运营主体（公司法人），梳理现有域名（example.com / api.dev.example.com） | 法务/运营 | 1 周 |
| 2 | ICP 备案：域名实名 + 接入商备案（阿里云备案系统）→ 获取备案号，网站首页展示 | 法务/运营 | 3-4 周 |
| 3 | 判断经营性质：IM + SaaS 交易若为经营性信息服务，办理 ICP 经营许可证 | 法务 | 并行 |
| 4 | EDI 评估：法务评估信息发布平台/交易处理是否落入 EDI 目录，如落入办理 EDI 许可证 | 法务 | 并行 |
| 5 | App 备案：按「移动互联网应用程序备案」提交 App 信息（客户端 + 服务器域名） | 运营/研发 | 2 周 |
| 6 | 等保：定级（建议二级；若大规模个人信息/关键设施则三级）→ 系统备案 → 等保测评 → 整改 → 取得测评报告 | 安全/研发 | 8-12 周 |
| 7 | CII 评估：确认是否被认定为关键信息基础设施，若落入按专项要求 | 法务/安全 | 并行 |

### 涉及系统
无代码改动；主要涉及法务、运营、安全、运维材料。

### 验收标准
- ICP 备案号获取并在官网/App 展示；等保测评报告齐备；App 备案完成。
- 资质清单形成台账，明确每项有效期与续期责任。

## P0-2 实名制（强制实名注册 + 账号信息审核）

### 目标
落实网络实名制（网络安全法 24 条），未实名不提供信息发布。

### 现状与差距
待确认是否强制手机号注册/实名核验；账号昵称/头像审核待确认。

### 方案
1. 手机号注册（强制）：注册即绑定手机号 + 短信验证码（复用现有短信能力）。
2. 实名核验（升级）：接入运营商三要素核验（姓名 + 身份证号 + 手机号）或二要素核验，将核验结果落库（仅存核验状态/脱敏，不存身份证明文）。
3. 未实名限制：未完成实名的用户只能浏览，禁止发送消息、建群、加好友、创建商户；发布信息前强制引导实名。
4. 账号信息审核：昵称/头像/签名接入敏感词过滤 + 违禁信息拦截；建立人工复审与封禁流程。

### 涉及系统
- im-user-service：注册流程、实名核验状态字段、权限判定。
- gateway / im-access-ws：未实名用户限制发言（鉴权/拦截）。
- 短信服务商 + 运营商核验接口（第三方）。
- 数据库：新增实名状态迁移（Flyway 只增）。

### 实施步骤
1. 迁移：user 表新增实名状态字段（real_name_status / verified_at，脱敏）。
2. 后端：新增实名核验接口（对接运营商），注册/登录链路接入。
3. 前端：注册/登录后引导实名；未实名弹窗与功能禁用。
4. 账号信息审核：昵称/头像提交时同步审核。

### 验收标准
- 新用户 100% 手机号实名注册；未实名无法发送消息/建群。
- 账号信息 100% 过审后才展示。

## P0-3 内容审核（全量审核链路 + 违法信息处置 + 举报）

### 目标
建立聊天内容审核能力，履行内容安全管理义务（网络安全法 47 条、网络信息内容生态治理规定）。

### 现状与差距
未发现内容审核链路；E2EE 私密聊天服务端不解密（见 P0-4）。

### 方案
1. 文本审核：敏感词库（本地词库 + 云端内容安全），支持变体/谐音/拼音识别。
2. 图片/音视频审核：接入云端内容安全（阿里云内容安全 / 腾讯天御），鉴黄/暴恐/违禁。
3. 审核架构：
   - 文本：发送时同步审核（gateway 或 message-service 前置），违规拒绝发送。
   - 图片/音视频/文件：异步审核（先发送，审核不通过自动撤回/删除 + 通知）。
4. 违法信息处置：违规内容记录（违规类型/时间/账号），提供删除/封禁/上报能力；建立向主管部门报告的流程与接口。
5. 举报入口：App 内会话/群组/消息举报入口，提交后进入管理后台工单；24h 内处置并反馈。

### 涉及系统
- 新增/复用「审核服务」：封装云审核 SDK（文本/图片/音视频）。
- gateway：文本消息前置审核。
- im-message-service：发送链路接入审核结果；异步撤回能力。
- im-admin-service / gv_chat_admin：举报工单、违法信息处置、上报台账。
- gv_chat_app：举报入口、违规提示。

### 实施步骤
1. 接入云端内容安全 SDK（文本/图片/音视频），封装为审核服务。
2. 文本同步审核接入发送链路；建立敏感词库与运营后台。
3. 图片/音视频异步审核 + 撤回链路。
4. 举报入口 + 管理后台工单 + 违法信息台账。

### 验收标准
- 明文文本 100% 过审；违规文本拦截。
- 违规内容 24h 内处置；举报 24h 内响应。
- 违法信息记录可追溯、可上报。

## P0-4 E2EE 合规（默认明文、可选加密、可配合监管）

### 目标
在保留私密聊天能力的同时，化解 E2EE 与内容审核义务的冲突。

### 现状与差距
私密聊天 E2EE 已部署，服务端仅存密文、无法解密，当前无任何合规边界（默认开启/无单独同意/无密钥托管预留）。

### 方案
1. 默认明文、可选加密：普通聊天保持服务端可审核；E2EE 仅作为用户主动开启的「私密聊天」，默认关闭。
2. 风险告知 + 单独同意：启用 E2EE 前弹窗明示「平台无法审核该会话内容，涉违法责任自负」，取得单独同意并记录同意时间。
3. 范围限制：E2EE 限一对一私密会话，禁止群聊 E2EE（群聊必须可审核）——当前已是一对一，补规则约束与校验。
4. 可配合监管的技术预留：
   - 企业/涉密场景：支持「密钥托管」（企业管理员托管解密密钥，用于合规审计与监管）。
   - 司法协查：预留「法院令状 + 密钥托管」的解密路径，避免完全不可监管黑盒（需法务评估方案）。
5. 商用密码合规：评估 X25519 + AES-GCM 与商用密码管理条例的兼容性；必要时引入 SM2/SM3/SM4 或完成合规评估备案。

### 涉及系统
- gv_chat_app / gv_chat_desktop：启用 E2EE 的单独同意弹窗 + 风险告知 + 默认关闭。
- im-conversation-service：私密会话创建校验（仅一对一、需同意标记）。
- im-message-service / im-user-service：密钥托管/恢复预留（企业场景）。
- 法务：密钥托管与司法协查方案评审。

### 实施步骤
1. 产品规则：私密聊天默认关闭 + 单独同意 + 一对一限制。
2. 客户端：启用弹窗与同意记录。
3. 服务端：会话创建校验同意标记与范围。
4. 密钥托管：企业场景托管密钥的接口与存储设计（可选，分阶段）。
5. 商用密码评估：算法合规评审。

### 验收标准
- 用户未单独同意无法开启 E2EE；E2EE 仅一对一。
- 普通聊天可被平台审核；密钥托管/司法协查路径方案落地。

## P0-5 隐私政策 + 单独同意

### 目标
落实个人信息保护法告知同意义务，提供完整隐私政策与敏感信息单独同意。

### 现状与差距
待确认是否有隐私政策；敏感个人信息（手机号等）单独同意、第三方 SDK 披露待确认。

### 方案
1. 隐私政策：编写完整隐私政策，明示——处理目的/方式/种类、保存期限、用户权利（查询/复制/更正/删除/注销）、第三方 SDK 清单、投诉渠道。
2. 首次启动同意：App/桌面端首次启动弹窗展示隐私政策，用户同意后才收集个人信息。
3. 单独同意：手机号、位置、未成年人信息等敏感个人信息取得单独同意（弹窗勾选）。
4. 第三方 SDK 披露：列明极光推送、阿里云短信/邮件、内容审核云服务等第三方及共享字段、处理目的。
5. 版本管理与撤回：隐私政策版本化，重大变更重新同意；提供撤回同意与注销入口。

### 涉及系统
- gv_chat_app / gv_chat_desktop：首次启动同意弹窗、单独同意、隐私政策页。
- 官网 example.com：隐私政策公开页。
- 法务：隐私政策文本审核签发。

### 实施步骤
1. 法务起草隐私政策 + 第三方 SDK 清单。
2. 客户端接入首次同意 + 单独同意 + 政策页。
3. 官网发布隐私政策。
4. 用户权利响应入口（导出/更正/删除/注销）闭环。

### 验收标准
- 隐私政策覆盖全部处理场景；用户未同意不收集。
- 敏感信息/第三方/未成年人均有单独同意。
- 注销/删除/导出可操作并限时响应。

## P0-6 敏感数据加密落地（正文 + PII + KMS）

### 目标
落地 SENSITIVE_DATA_PROTECTION.md 的 Phase1/2，确保消息正文与 PII 不以明文落库/缓存/MQ/日志/备份。

### 现状与差距
应用层信封加密仍为 Proposed（未落地）；密码已 BCrypt 哈希（合规），但消息正文、手机号、邮箱、设备 token 明文存储风险高。

### 方案
1. Phase1（PII，2-4 周）：手机号/邮箱/设备 token 应用层加密 + HMAC 检索令牌（保留精确查询能力）。
2. Phase2（消息正文，3-5 周）：MySQL 权威消息、MongoDB 热投影、Redis 缓存、RocketMQ 载荷中的正文改为密文（AES-256-GCM 信封格式）。
3. KMS：接入阿里云 KMS（国内）或 Vault，KEK/DEK 分层，密钥版本化 + 轮换。
4. 日志脱敏：Logback/JSON 脱敏器 + HTTP 请求响应脱敏，禁止日志含明文正文/PII。
5. 权限最小化：每服务独立 ServiceAccount + KMS 最小权限；管理员查看原文需审批 + 审计。

### 涉及系统
- sdk/infrastructure：新增 SensitiveData SDK（EnvelopeCrypto/Masker/SearchToken/PolicyEnforcer）。
- im-user-service / im-message-service / im-access-ws：接入加密读写。
- MongoDB/Redis/RocketMQ：字段/载荷切换密文。
- 运维：KMS、密钥轮换、备份加密、网络隔离。

### 实施步骤
1. 数据资产盘点（字段级清单）+ CI 敏感字串扫描阻断明文落日志。
2. 实现 SensitiveData SDK + KMS 客户端 + 单元测试。
3. Phase1：PII 加密 + 检索令牌，新旧字段双写、读优先密文、灰度切换。
4. Phase2：消息正文全链路密文（MySQL/Mongo/Redis/MQ）。
5. 密钥轮换 + 恢复演练 + 权限回收演练。

### 验收标准
- S3/S4 字段（正文/PII）不以明文出现在 MySQL/MongoDB/Redis/RocketMQ/日志/备份。
- 未授权管理接口只能得到脱敏结果；原文查看需审批 + 审计。
- 业务功能（收发/离线拉取/未读/撤回/推送/手机号邮箱精确查询）不受影响。
