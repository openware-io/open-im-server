# 可观测性规范

## 目标与范围

可观测性用于在不依赖临时复现的情况下，识别系统状态、定位故障、评估风险并支撑审计。本规范适用于业务服务、网关、异步任务、消息消费者和基础设施适配器。

本规范定义日志、指标、链路追踪、告警、审计和敏感信息保护的共同边界；专项实现规则分别由 [41 Java 日志规范](./41_JAVA_LOGGING_CONVENTIONS.md) 与 [42 日志输出与诊断规范](./42_LOGGING_AND_OUTPUTS.md) 约束。

## 术语与前置假设

| 术语 | 定义 |
| --- | --- |
| 信号 | 日志、指标、链路追踪三类可观测性输出；审计作为独立合规信号单列。 |
| 关联标识 | 能把一次操作跨服务串起来的标识（请求 ID、消息 ID、追踪 ID）。 |
| 口径 | 指标名称、单位、标签与聚合方式的一致约定。 |
| 传播 | 关联标识跨进程、跨消息的传递。 |
| 脱敏 | 在信号产生或采集环节移除凭据与个人信息的处理。 |

**前置假设**：各服务具备统一日志门面与采集通道；存在可用的指标与追踪后端；审计存储独立于业务库。

## 统一原则

1. 每一条关键业务链路必须具备可关联的日志、指标或追踪证据，不能依赖临时增加日志才能定位问题。
2. HTTP、RPC、WebSocket、MQ、定时任务等入口必须传播或生成关联标识；跨边界日志必须携带足以关联请求、事件和业务实体的标识。
3. 可观测性数据必须服务于业务定位、容量评估、告警处置或审计；禁止无目的记录全量载荷。
4. 密钥、令牌、密码、完整消息正文、敏感个人信息和未经脱敏的身份凭据不得写入日志、指标标签、追踪属性或诊断文件。
5. 指标标签必须是有限集合；禁止将用户 ID、会话 ID、消息 ID、请求 ID 等高基数字段作为指标标签。
6. 告警必须对应明确的影响、阈值、责任方和处置步骤；仅有监控面板而没有告警策略不构成可运维能力。
7. 审计记录必须与普通运行日志区分保留策略、访问权限和完整性要求。

## 信号职责

| 信号 | 用途 | 必须避免 |
| --- | --- | --- |
| 日志 | 记录关键决策、状态变化、失败上下文和业务关联标识 | 全量对象、敏感字段、缺少上下文的异常 |
| 指标 | 反映吞吐、时延、错误率、饱和度和业务积压趋势 | 高基数标签、用指标替代事件明细 |
| 链路追踪 | 还原跨进程调用和异步链路关系 | 将完整载荷或凭据写入 Span 属性 |
| 告警 | 在用户影响或风险超过阈值时触发处置 | 无负责人、无阈值、无运行手册的告警 |
| 审计 | 留存安全敏感或合规关键操作的不可抵赖证据 | 与调试日志混存、允许任意删除或篡改 |

## 最小要求

1. 服务启动、停止、配置加载失败、关键依赖不可用、主链路失败和异步消费失败必须可被检索和告警。
2. 关键入口与关键输出必须记录关联标识；字段选择和日志级别遵循 [41 Java 日志规范](./41_JAVA_LOGGING_CONVENTIONS.md)。
3. 构建、验证、部署和本地诊断输出必须按 [42 日志输出与诊断规范](./42_LOGGING_AND_OUTPUTS.md) 统一归档。
4. 新增服务或关键链路时，必须在服务文档中声明关键指标、告警条件、关联标识和故障处置入口。

## 验收与演进

1. 新增关键链路的评审必须检查日志上下文、指标口径、追踪传播、告警条件和敏感信息脱敏。
2. 发生无法定位、告警失效或敏感数据泄露风险的事故后，必须补充对应规范、门禁或运行手册。
3. 指标、追踪、告警和审计的专项规范建成后，必须继承本规范的统一原则，不得改变其安全与关联边界。

## 接入模板

**新增一条关键链路时，按此清单落地（示例，措辞不构成强制）**：

1. **关联标识**：在入口（HTTP/RPC/WS/MQ/定时任务）生成或接收关联标识，并在跨边界处传播。
2. **日志**：关键输入、关键输出与状态切换各有一条带关联标识与业务实体的记录（写法见 Java 日志规范）。
3. **指标**：为成功率、时延与失败原因选择或新增指标；名称、单位与标签遵循既有口径，不新建同义指标。
4. **追踪**：确认跨服务与跨消息的链路可串接；异步消费保留父链路标识。
5. **告警**：给出触发条件、严重级别、通知对象与处置入口；避免只告警不处置。
6. **脱敏**：确认信号中不含凭据、签名 URL 与个人信息。

```text
入口: 收到请求 -> 取/生成 requestId(或 traceId)
处理: log.info("动作, requestId={}, bizId={}", rid, id)
出口: metric{name, outcome, latencyMs} ++;  告警规则绑定 name 与 outcome
异步: 消息头携带 traceId -> 消费者续接链路
```

## 可验证的验收标准

| # | 判据 | 证据形式 |
| --- | --- | --- |
| 1 | 一条关键链路可在日志、指标或追踪中关联定位，无需临时加日志 | 该链路的一次查询结果 |
| 2 | 跨边界处关联标识已传播（HTTP/RPC/WS/MQ/定时任务） | 两端日志或追踪片段 |
| 3 | 指标名称、单位与标签遵循既有口径，无同义重复 | 指标清单对照 |
| 4 | 每条告警都有触发条件、级别、通知对象与处置入口 | 告警规则清单 |
| 5 | 信号中不含凭据、签名 URL 与个人信息 | 抽查日志与指标标签 |

**完成定义**：上表逐项有可复现证据，且统一工程校验入口在该范围退出码为 0。

## 门禁与人工检查项

**可自动化**：

| 门禁 | 判据 |
| --- | --- |
| 日志脱敏 | 日志与指标标签中不出现 token、签名 URL、个人信息或原始硬件标识 |
| 关联标识存在 | 入口适配器（HTTP/RPC/WS/MQ/定时任务）在日志与消息头中携带关联标识 |
| 指标口径唯一 | 同名指标不在不同模块重复定义；单位与标签一致 |

**人工检查项**（新增关键链路评审时确认）：

1. 该链路的日志上下文、指标口径、追踪传播、告警条件与脱敏是否逐项具备。
2. 告警是否给出触发条件、级别、通知对象与处置入口。
3. 失败路径是否也能被观测（不是只在成功路径打点）。
