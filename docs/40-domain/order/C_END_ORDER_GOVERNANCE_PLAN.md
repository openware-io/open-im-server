# C/B 端订单主流程治理方案

> 范围：C 端消费应用（酒店/KTV）、B 端门店运营、SaaS 后台订单可见性。
> 基线：`develop/2.4.0-hotel`；所有变更走迁移只加不改、门禁、PR 合并 main。

## 1. 治理目标

用户下单成功后，必须能在 C 端“我的”、B 端门店工作台、SaaS 后台看到同一笔业务，并且状态、金额、归属一致。

验收不只看 `201/200`，必须包含：

```text
C 下单成功
→ C 我的预约 / 酒店订单 / 我的消费可见
→ B 门店经理列表可见并可响应
→ SaaS 后台可见
→ 状态与金额一致
```

## 3. 治理阶段

### Phase 1：阻断可见性问题（已完成）

- C 酒店订单按 `bookedByAccountId + tenantId` 聚合；
- C 酒店下单前初始化会员，服务端强校验 `customer_id`；
- `V31__backfill_c_hotel_order_customer.sql` 幂等回填历史订单；
- C H5 增加“酒店订单”入口、`PENDING_CONFIRM` 映射、部分失败提示；
- B 酒店列表分页、确认 expectedVersion、手机号归属会员校验；
- ADR-0023 建立 ConsumerContext/资源门店/用户订单读模型边界；
- 回归：酒店 E2E 142/142，KTV 闭环通过，C H5 174 tests。

### Phase 2：统一读模型与全量分页（待实施）

- 落地 ADR-0009 `ord_user_order_index`，C“我的订单”单入口；
- `displayStatus` 进入 OpenAPI 契约，后端投影酒店/KTV 统一用户状态；
- B/C 所有列表统一 cursor/limit、默认日期范围；
- 历史订单回填巡检与告警；
- 测试数据 fixture 隔离和自动清理。

### Phase 3：安全与可观测性

- B 端手机号归属审计、PII 脱敏矩阵；
- C 会员自动开通的同意、审计、限流；
- C/B 403、空列表、状态不一致指标；
- 跨门店写入门店的审计查询。

## 4. 工程门禁

每个变更必须：

1. 迁移只加不改，数据修复独立、幂等、可在 dry-run 中评估；
2. 公共 API 变更同步 `docs/30-reference` / `docs/50-services`，并登记 ADR；
3. 运行 `invoke-engineering-validation.ps1 -Scope Changed`；
4. 单元测试覆盖授权/归属/幂等/空值；
5. E2E 覆盖 C → B → SaaS 可见性，不只断言 HTTP 201；
6. 通过 PR 合并 main，不直接 push main；
7. 验证数据清理或明确保留原因。

## 6. 当前结论

Phase 1 阻断问题已关闭；Phase 2/3 作为同一治理项目的后续工作，不得以“修好一个页面”视为整体完成。
