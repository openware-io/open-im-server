# 酒店业务决策与待确认问题

[中文](HOTEL_DECISIONS.md) | [English](HOTEL_DECISIONS.en.md)

> 状态：`draft`（`develop/2.4.0-hotel`）  
> 用途：把“已经建议的默认值”和“必须业务拍板的问题”分开，避免开发替产品做决定。

## 已建议的默认决策

| 编号 | 决策 | 理由 | 状态 |
| --- | --- | --- | --- |
| H-D01 | 酒店库存按**房型**卖，入住时分配具体房间 | 与主流 OTA/酒店 PMS 一致；避免用户先选房号 | 建议 |
| H-D02 | 复用 `platform-resource-service` 的资源/房型能力，不新建 hotel-service | MVP 控制分布式复杂度；保留拆分触发器 | 建议，待评审 |
| H-D03 | 酒店预订订单放 `platform-order-service`，不复用 KTV `Reservation` | 酒店是日期区间 + 房型库存，KTV 是时间点 + 包厢 | 建议 |
| H-D04 | 金额用最小货币单位 + 币种 | 遵守现有币种规范 | 建议 |
| H-D05 | 下单先 hold 库存，支付成功再 consume | 防止超卖和未支付占房 | 建议 |
| H-D06 | 所有写接口要求 `Idempotency-Key` | 支付回调和重试必须幂等 | 建议 |
| H-D07 | 取消政策按 `RatePlan` 配置，不写死 | 不同价格计划政策不同 | 建议 |
| H-D08 | 住客证件号加密存储、日志脱敏 | 安全与合规底线 | 必须 |

## 必须拍板的问题

| 编号 | 问题 | 选项 | 影响 |
| --- | --- | --- | --- |
| H-Q01 | 业务形态是单店、连锁还是多门店？ | 单店 / 多门店 / 集团连锁 | 决定是否现在做集团 CRS、中央库存 |
| H-Q02 | 支付模式？ | 全额预付 / 定金 / 到店付 / 担保 | 决定订单状态机、退款、no-show |
| H-Q03 | 是否接 OTA/渠道经理？ | 不接 / 接携程美团 / 自建渠道 | 决定库存同步、渠道映射、超卖策略 |
| H-Q04 | 前台操作端？ | Admin Web / 移动端 / 两者 | 决定 BFF 与页面范围 |
| H-Q05 | 是否需要发票、押金、公安登记？ | 需要 / 不需要 / 二期 | 决定字段、合规接口、财务流程 |
| H-Q06 | 会员/积分/优惠券是否参与？ | 不参与 / 优惠券 / 全量 | 决定与 customer/marketing 的集成 |
| H-Q07 | 多币种是否 MVP？ | 人民币 / 多币种 | 决定价格与结算模型 |
| H-Q08 | 原型是否还有未展示页面？ | 有 / 无 | 避免按不完整原型建模 |

## 建议的决策记录方式

- 业务范围决策：本文件 + 产品确认；
- 架构边界决策：新增 ADR（例如“酒店库存归属 resource 域”）；
- 数据模型/接口：进入实现后以迁移和 OpenAPI 为准；
- 任何默认值被推翻，必须更新本文件和实现方案，不能只在聊天里说。
