# ADR 0017：权限目录矩阵的单元格语义、范围边界与授权并发控制

## Status / 状态

**proposed（提案中，2026-10-29）**。本 ADR 决定权限目录矩阵（平台后台 `/admin/iam/permissions`）的单元格状态模型、一期数据范围、授权写入的乐观并发控制与页面新鲜度策略；不改变 ADR-0014 / ADR-0015 已确立的 Tenant Access 归属、角色绑定主体与作用域枚举。

## Context / 背景

权限目录页新增“权限列表 + 全局角色矩阵”后，暴露了三类问题：

1. **单元格语义不完整**：UI 只有“授予/未授予”两态。权限本身带有 `grantableLevels`，角色带有 `scopeLevel`；当“已授予”但权限不允许该角色作用域时，这是越界/历史遗留授权，不能与正常授予画同一个 `✓`。当前实现把所有非授予都画成 `—`，把越界授予画成正常 `✓`，矩阵无法承担治理职责。
2. **范围边界不清**：矩阵只展示 `iam_role.tenant_id IS NULL` 的全局角色模板（预置 + 平台自定义），不展示租户自定义角色与实际角色绑定。页面若不明确标注，会被误读为“全平台实际授权”。
3. **编辑并发与页面新鲜度**：角色权限编辑是“读取整个集合 → 整体替换”，没有版本校验，两个管理员并发保存会静默丢失修改；目录页只在 `onMounted` 加载一次，其他管理员修改后当前页面不会发现服务端版本已变化。

约束：

- 权限/角色的授权语义判定在领域模型 `Permission.grantableTo(roleScopeLevel)`，前端不能复制一套规则；
- 角色权限写入必须继续走 `IamAuthorizationApplicationService` 的作用域校验与审计；
- 目录矩阵是平台级只读字典，不要求租户上下文（与 `GET /admin/iam/permissions` 同口径）；
- 服务端已有“数据库版本键控”的矩阵缓存，版本由 IAM 表事实派生，不引入广播失效。

## Decision / 决策

### 1. 四态单元格，授权规则由服务端计算

矩阵 API 为每个角色返回两组编码：

- `permissionCodes`：已授予的权限编码；
- `grantablePermissionCodes`：按角色 `scopeLevel` 调用 `Permission.grantableTo` 计算出的可授予权限编码。

前端据此渲染四态：

| 状态 | 条件 | 展示 |
| --- | --- | --- |
| granted | 已授予且可授予 | 绿色 `✓` |
| grantable | 可授予但未授予 | 蓝色 `○` |
| forbidden | 不可授予 | 灰色 `—` |
| anomaly | 已授予但不可授予 | 红色 `⚠`，计入异常统计并可筛选 |

前端只做集合查表，不重复实现授权规则；新增权限/角色作用域时只改服务端领域判定。预置角色授权元数据由 V36 校准（ADR-0018），矩阵异常应为 0。

### 2. 一期范围：只做“全局角色模板”矩阵

一期矩阵列只包含全局角色（`tenant_id IS NULL`），页面与接口明确标注“模板，不含租户自定义角色与实际绑定”。

**非目标**：不在本期把租户自定义角色、`iam_role_binding` 并入同一矩阵。该能力需要租户上下文、租户隔离与独立的读取权限，另立 ADR/设计；本期不改变现有租户角色编辑页的数据口径。

### 3. 角色权限写入采用“行锁 + 版本 CAS”

- 新增 `GET /admin/iam/roles/{roleId}/permissions/snapshot`，返回 `permissionCodes + version`；
- 角色权限版本由“角色最后更新时间 + 该角色授权数量 + 授权集合 CRC 校验和 + 授权最后更新时间”派生；
- `POST /roles/{roleId}/permissions` 和 `POST /roles/{roleId}/permissions/toggle` 接受可选 `expectedVersion`；
- 写事务先对 `iam_role` 行 `SELECT ... FOR UPDATE`，再做版本校验，最后替换/增删授权；版本不匹配返回 `409 PERMISSION_VERSION_CONFLICT`；
- 不传 `expectedVersion` 时保留旧调用方的无条件写入语义（兼容期），新 UI 必须传版本。

选择 CAS 而非全局目录版本：全局版本会让无关角色变更导致冲突；选择行锁 + 角色版本是为了让“同一角色的并发写”串行化，同时允许不同角色并行编辑。

### 4. 页面新鲜度：版本校验 + 聚焦检查

新增 `GET /admin/iam/permissions/matrix/version`，只返回目录版本（不读业务行、不读缓存）。

目录页在窗口重新聚焦/从后台可见时调用该接口：版本变化只显示“数据已更新”提示，由用户选择刷新；不自动替换用户正在阅读的矩阵。矩阵本身的服务端缓存仍按版本键控，下一次请求必然拿到新数据。

### 5. 缓存与鉴权边界不变

- 矩阵缓存继续使用“数据库版本键 + Redis/本地 + TTL 10 分钟”，不做主动广播失效；
- 目录矩阵读接口保持平台级只读字典口径，不要求租户上下文；角色权限读写接口继续走既有上下文与作用域校验；
- 角色权限读取增加归属校验：平台上下文可读全局角色，租户上下文可读全局预置 + 本租户角色，跨租户按 roleId 读取返回 403；
- 本期不新增数据库表/迁移，不改变权限/角色表结构。

## Consequences / 后果

正向：

- 矩阵从“对照表”升级为可发现越界授权的治理视图；
- 角色权限编辑并发安全，避免静默覆盖；
- 页面打开后能发现服务端版本变化，不再无限期显示旧数据；
- 四态由服务端领域规则派生，前后端不会出现授权语义漂移。

代价与约束：

- 矩阵响应增加 `grantablePermissionCodes`，响应体略增；只读缓存仍缓存领域快照，转换在请求时计算；
- 角色权限写路径增加一次角色行锁与一次版本查询，写吞吐略降；只影响角色授权写入；
- 前端列表刷新从“仅手动”变为“可发现过期”，需要维护版本状态与错误处理；
- 一期仍不覆盖租户自定义角色/实际绑定，后续需要独立 ADR 扩展范围。

实现后实测（本地 kind 数据）：**67 项预置角色跨作用域授权**（`platform.operator` 54、`tenant.owner` 12、`store.manager` 1），自定义角色 0。根因是 V1 3.10/3.11 预置种子给角色授予了经营权限，但未同步更新权限的 `grantable_levels`。ADR-0018 决定通过 **V36 数据校准**把对应 `PLATFORM` / `TENANT` / `STORE` 追加到这些权限的可授予范围，不删除任何既有授权；校准后矩阵异常应为 0，矩阵恢复统一四态，不再维护“预置基线例外”。

## Alternatives considered / 备选方案

1. **前端自行按 `grantableLevels` 计算可授予**：拒绝。会复制授权规则，前端/后端作用域变化时容易漂移。
2. **全局目录版本作为写 CAS**：拒绝。任何与目标角色无关的 IAM 变更都会制造 409，编辑体验差。
3. **数据库唯一约束/触发器实现 CAS**：拒绝。跨多行替换授权难以用单条约束表达，且会引入 MySQL 触发器维护成本；行锁 + 版本查询更贴合现有 MyBatis-Plus 事务模型。
4. **自动轮询/SSE 实时推送**：本期拒绝。权限矩阵是低频治理页面，聚焦检查 + 手动刷新足够；实时推送引入连接与部署复杂度。
5. **本期直接并入租户自定义角色矩阵**：拒绝。涉及租户上下文、数据隔离和独立权限，需另立 ADR，不能以“页面看起来完整”为由扩大数据暴露面。
