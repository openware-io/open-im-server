核心模型：两条正交轴

每个菜单节点、每个权限码都必须同时声明 scope_level + domain_code
层级 ＼ 功能域 core 跨业态内核 ktv KTV hotel 酒店 spa / massage retail 超市
PLATFORM 平台运营 · tenant_id 可空 租户管理平台角色/权限支付渠道授权 ————
TENANT 租户 = 集团主体 · tenant_id 门店管理币种支付渠道（默认） 通用目录会员/积分/储值 运营人员角色权限脱敏权限审计日志 业态模板服务项目 房型定义 技师等级 分类模板
ORGANIZATION 品牌/事业部 · 一期仅模型位 组织级报表组织策略下发 ————
STORE 门店 · 数据隔离最细粒度 订单预约收银/退款 交班/日结库存资源管理 计价方案门店商品门店报表门店信息 包厢看板开台/结台服务人员 计时计费KTV 配置 房态看板入住/退房房价 技师排班房间/钟房 收银台条码/称重
归属判定唯一口径：看该功能的权威数据主键里有没有 store_id。
有 → 门店级（同一功能在 N 家门店就是 N 份数据）；只有 tenant_id → 租户级；只有 organization_id → 组织级；无租户约束 → 平台级。
「同一业态开多家店」不改变菜单结构——门店级菜单对每家店都一样，只是数据不同；跨店对比能力放租户级「经营总览」。

通用 vs 门店独立：全库 114 张表实测分类新增

扫描 138 个 Flyway 迁移得出，不是语义推断
A · 租户通用
跨店共享一份数据，新增业态零改动
只有 tenant_id
cst_member cst_point_account cst_point_ledger cst_wallet_account cst_wallet_ledger mkt_campaign mkt_coupon mkt_coupon_issuance mkt_coupon_redemption mkt_consent tnt_tenant tnt_organization tnt_legal_entity tnt_tenant_config tnt_business_type iam_role iam_audit_log saa_admin_account idt_account
会员 / 积分 / 储值 / 营销 / 租户 / 组织 / IAM —— 酒店、按摩、超市全部直接复用。
储值账户挂 legal_entity_id（法人主体）而非门店，是正确的商业决策。
B · 门店独立
每家店一份，天然要求上下文带 storeId
store_id NOT NULL
ord_order+business_type ord_reservation+business_type res_resource+resource_type res_room_type res_occupation res_schedule ord_inventory_material ord_inventory_stock ord_inventory_transaction ord_product ord_product_category tnt_pricing_plan pay_shift pay_daily_closing pay_intent pay_channel_provider
ord_order 四层键齐全：tenant_id + organization_id + store_id + business_type，是标准范本。
res_resource.resource_type 用枚举承载业态，一张表服务所有业态。
C · 混合：租户定义 + 门店覆盖 ★
分层能力的关键，当前只有 3 张表做到
store_id NULL = 租户默认
ord_catalog_item完整 pay_channel_config完整 res_room_type.unit_price仅价格字段 iam_user_role三层作用域
ord_catalog_item 与 pay_channel_config 的列注释明写「NULL=租户级」，是现成范本。
iam_user_role 的授权继承已完整可用（见第 6 节）。 
-- 分层范本：照抄这个模式
store_id bigint unsigned NULL
  COMMENT '门店ID，NULL=租户级通用'

-- 读：COALESCE(门店行, 租户行)
-- 写：门店行覆盖租户行
D · 派生门店级 ⚠️ 最大技术债
无 store_id，靠父键间接归属
store_id 缺失
ord_order_item ord_ktv_session ord_ktv_server_session pay_collect pay_refund pay_transaction
归属路径：order_id → ord_order.store_id
后果：门店级权限 / 报表 / 审计若要按 store 收敛，这些表无法直接过滤，必须 JOIN 回 ord_order。
建议：写时冗余 store_id + business_type（订单创建时一起写、不可变），读时直查。
E · 平台级（无租户约束）
tenant_payment_method pay_channel_provider（平台侧） saa_admin_account
tenant_payment_method 是「平台授予租户某项支付能力」的开关，AdminMenuApplicationService.isWalletGranted() 就是查它来决定「储值管理」菜单是否下发 —— 这是 required_grant 剪枝规则的现成实现。
新增功能时的决策树：
① 这张表的权威数据是不是每家店一份？　是 → B 门店独立，store_id NOT NULL，菜单挂门店段。
② 不是，但允许门店覆盖？　是 → C 混合，store_id NULL = 租户默认，读用 COALESCE。
③ 都不是 → A 租户通用，只有 tenant_id，菜单挂租户段。
绝不允许出现 D —— 归属靠父键推断的表一多，门店级权限就是空谈。

AND (#{storeId} IS NULL OR ur.store_id IS NULL OR ur.store_id = #{storeId})
即「上下文维度为空 = 全放行」：租户级绑定（store_id IS NULL）对名下所有门店生效，组织级绑定对本组织所有门店生效。
本方案只补两件事：① 给权限加 scope_level 元数据，让授权界面能按层级分树、能拦住「门店级权限授到租户级」； ② 给菜单加 scope_level，让它渲染在正确的那一段。

五处缺口与技术债新增

其中 1 / 2 / 4 都动表结构，建议在 M1 之前先把地基打平
#缺口严重度 影响建议
1 tnt_pricing_plan.store_id NOT NULL 高 A380 开 3 家 KTV 要配 3 遍计价方案；且它挂在 scope=PLATFORM 的 /admin/pricing-plans 下 —— 层级和归属双重错位 改 store_id NULL = 租户默认；菜单归入门店设置的业态域
2 派生子表无 store_id
ord_order_item · ord_ktv_session · pay_collect · pay_refund · pay_transaction		 高 门店级权限 / 报表 / 审计无法直接收敛，必须 JOIN 回 ord_order。这是「门店级菜单与权限」能不能真正落地的最大障碍 写时冗余 store_id + business_type（订单创建时一起写、不可变）；读时直查
3 iam_audit_log 无 store_id 中 门店级审计只能翻 detail_json，无法过滤 / 索引 加可空 store_id
4 mkt_campaign_scope 「首发骨架不建」 高 优惠券的「业态及门店范围」在 SAAS_PLATFORM_01 §营销里承诺了但未实现；rule_snapshot_json 注释直接写「不可查询」 补 mkt_campaign_scope（scope_type / business_type / store_id）
5 cst_member 无门店线索 低 会员跨店通用是正确商业决策，但「办卡门店 / 归属门店」这类运营诉求无处落 加 origin_store_id（可空，仅记录，不参与隔离）
为什么缺口 2 最要紧：本方案要让「门店级功能放在门店层次」，前提是门店级数据能被可靠地按 store_id 切分。 现在订单明细、KTV 会话、支付退款这几张最核心的事实表都只能靠 JOIN 推断门店 —— 菜单分好了层，权限却收敛不下去，等于只做了一半。
