# B 端 App 交互原型与体验规范

> **变更记录（v2）**：首发收敛为 KTV——原型聚焦「包厢看板 / 快速开台 / 计时加项 / 结台 / 收银 / 交班」，房务与酒店/足浴场景降为后续。

## 1. 定位

本文件是 `SAAS_PLATFORM_03_APP` 的交互实施依据。它定义门店员工在高频、时间敏感操作中的页面层级、确认点、失败恢复和跨角色交接，不替代 REST/状态机的权威规则。

原型优先覆盖首发闭环（KTV）：登录与门店选择、工作台、包厢看板、快速开台、订单执行、收银、交班、审批。PC Admin 承担复杂配置；B App 只承担移动运营执行。

## 2. 全局交互原则

1. 当前租户、门店、班次和角色始终在顶部可见；切换门店必须二次确认并清理业务缓存。
2. 资源看板优先显示状态和下一步动作，不能只显示静态日历。
3. 资金、入住、开台、派技师、换房、退房、交班均须显示订单/资源/金额/影响并要求确认。
4. 后端返回的 `allowedActions` 决定按钮状态；无权限与状态不允许均不展示伪可操作入口。
5. 任何写操作展示提交中状态，成功后刷新权威详情；超时显示“处理中”，不得显示“失败后可随意重试”。
6. 高风险操作要求原因；退款、作废、反结要求审批状态页，申请与完成使用不同文案和颜色。

## 3. 信息架构与底部导航

| 导航 | 使用者 | 一级目标 |
| --- | --- | --- |
| 工作台 | 全部角色 | 待办、经营摘要、班次和快捷操作 |
| 资源 | 收银、店长、服务员、前台 | 包厢状态与进入订单 |
| 订单 | 收银、店长、服务员 | 快速开台、订单列表、计时加项和结算 |
| 我的 | 全部角色 | 班次、审批、门店切换、账号与退出 |

角色无权访问的导航项不显示。收银入口在工作台和订单页均提供，但仅收银员/店长可见。

## 4. 核心原型流

### 4.1 登录与上下文选择

```text
登录 → 加载可用上下文
  → 仅一个有效门店：自动选择并提示当前门店
  → 多个上下文：选择租户 → 组织（如有）→ 门店
  → 获取权限菜单 → 工作台
```

上下文选择页显示租户名称、门店名称、国家/币种、角色和最近使用时间；不显示其他租户的客户、订单或经营数据。门店切换前若存在资金处理中订单，显示阻止提示并要求先完成/查询结果。

### 4.2 工作台与待办

顶部显示“门店/角色/班次”；首屏仅显示本班营业额、待办数、在用资源数和待审批数。待办按紧急度排序：待入住/待开台、待服务、待清洁、待结算、待审批。点击待办进入对应订单或资源详情，不在工作台完成资金操作。

### 4.3 资源看板

资源看板首发仅 KTV 包厢。每个格子只显示包厢编号、状态和最必要的时间/人员摘要；颜色必须同时配合文字状态。

| 状态 | 点击后动作 |
| --- | --- |
| 可用 | 有权限者进入快速开台/预订 |
| 已预留 | 查看预订、到店或取消入口 |
| 使用中 | 进入订单工作台 |
| 不可用 | 显示原因，不提供开台 |

资源页面下拉刷新；前台每 15–30 秒刷新一次并展示最后更新时间。资源状态版本变化后，本地详情必须回源刷新。

### 4.4 快速开单与履约

快速开台：选择包厢和时段，再选择客户（可跳过或创建待认领客户）和加项商品/服务。每一步即时请求后端可选包厢/价目，不能用本地过期价格完成提交。

| 业态 | 最短路径 |
| --- | --- |
| KTV（首发） | 选择包厢和时段 → 开台 → 计时 → 加项 → 结台 → 收款 |

开单提交成功必须返回订单号、资源状态和下一步允许动作。资源冲突、版本冲突或价格变化时保留用户已选项，提示重新选择/确认，不能静默替换资源或金额。

### 4.5 订单工作台

订单页固定显示订单号、业态、公共状态、专属履约状态、资源、客户脱敏信息、金额与支付摘要。操作按权限分组：履约、加项、优惠、收银、异常。付款前后均展示服务端计算的明细，不允许编辑总价。

服务员只能看到与自己关联的服务卡片和“加项、加钟、完成服务”动作；店长/收银可见结算；房务只见清洁任务。订单状态更新后展示时间和操作者。

### 4.6 收银与支付

收银页分为“应收明细 → 可用支付方式 → 支付处理中/结果”。可用方式只能来自 `available-methods` 接口，客户端不自行展示支付宝、微信、Stripe 或储值。

组合支付时，用户逐笔输入不超过剩余应收的金额；每笔成功后由服务端返回剩余金额。支付处理中退出页面后，订单卡显示“处理中”，重新进入只能查询原支付意图。退款、退押金和作废始终进入申请/审批流，不能在收银页直接完成。

### 4.7 交班与审批

交班页显示当前班次、渠道汇总、应有现金、实盘现金、差额和异常备注。差额不为零时必须填写原因；提交后进入待复核或已关闭状态。

审批列表显示申请类型、门店、金额、申请人、原因和原订单摘要。审批弹窗显示不可修改的申请金额与可审批金额范围；申请人、同一操作人和无范围角色不能审批。

### 4.8 房务（后续，酒店场景）

房务为酒店场景能力，KTV 首发不启用；KTV 结台后包厢直接释放为可用，无清洁环节。

## 5. 页面状态与反馈矩阵

| 场景 | 页面行为 |
| --- | --- |
| 首次加载 | 骨架屏，不显示旧门店数据 |
| 空数据 | 明确说明原因；若有权限提供创建入口 |
| 无权限 | 不展示敏感内容；显示返回工作台 |
| 网络不可用 | 展示缓存与时间；资金/履约写按钮禁用 |
| 401 | 清理 B 端会话并回登录 |
| 上下文过期 | 保留全局登录，回门店选择 |
| 订单版本冲突 | 保留表单草稿，刷新权威详情后要求重新确认 |
| 支付超时 | 显示处理中，提供“查询结果”，不提供“再次支付” |
| 审批提交成功 | 显示“已提交审批”，不显示退款/作废已完成 |

## 6. 原型评审与交付要求

在编码前，产品、门店运营、财务和开发共同评审以下低保真原型：

- 店长工作台与门店切换；
- KTV 开台/计时/加项/结台；
- 收银组合支付、支付处理中和退款申请；
- 交班差额与审批；
- 无网、包厢冲突、权限不足、支付超时四类异常。

每个评审通过的页面必须记录：页面编号、角色、前置状态、调用 API、成功/失败/空态/权限状态、埋点事件和关联 E2E 编号。视觉高保真稿在低保真操作流确认后再产出，禁止先做静态视觉稿再倒推业务状态。

## 7. 实施验收

- [ ] 所有 `BAPP-E2E-*` 用例均有对应原型页面和异常态。
- [ ] 原型中每个按钮可映射到 `SAAS_PLATFORM_05_API` 的命令或明确的只读导航。
- [ ] 不存在客户端直接改变金额、资源状态、支付结果或审批结果的交互。
- [ ] C 端路由、聊天、通话和预约体验不被 B 端导航或依赖改动影响。
- [ ] 房务、服务员、收银、店长、财务在原型中只看到其最小必要信息与动作。
