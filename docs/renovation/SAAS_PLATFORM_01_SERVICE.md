# 第二阶段多业态 SaaS 平台业务方案

> **变更记录（v2.0.0）**
> - **首发业态收敛为 KTV**：酒店、足浴、普通收银/零售降为后续演进，不阻断 KTV 首发。
> - **IM 与 SaaS 独立产品化**：两者数据库独立、代码独立、独立部署、可独立销售；仅共享公共工程规范/技术框架/公共依赖（公共层）。IM 聊天仅作为 C 端入口之一，通过授权登录（OAuth）+ 用户信息同步打通；SaaS 业务系统拥有独立账号与业务闭环，不依赖 IM 运行。
> - **通用支撑域**：跨业务通用运行能力（媒体、审核、邮件、短信、支付）独立成域（`common-services/`、`common-*`）；`common-media-service`→`common-media-service`；支付域（支撑域子域，下探一层）= 支付业务（`common-payment-service`）+ 支付渠道（`common-payment-channel-service`）。
> - **公共 SDK 目录**：`sdk/`→`sdk/`。
> - **版本与分支**：版本统一 2.0.0；所有仓库合并主干提交后，从主干建立新的大版本开发分支 `develop/2.0.0-saas-20260826`。
> - **储值币/代币术语**：业务术语「储值币/代币」，默认展示名「A380币」（租户级可自定义，`tnt_tenant_config.wallet_brand_name`）。
> - **业态扩展**：代码 + 配置——业态专属履约/资源/计价写代码，统一订单/资金/会员/营销/IAM 不随业态新增而改动。
> - **组织层级**：一期一层（租户→组织→门店），多层组织树后续演进。
> - **会员/积分/储值共享**：默认集团级（租户）通用，可配门店范围；储值跨币种仍默认关闭。
> - **B 端 App**：一个 App + 业态模块化（按 `store.business_type` 渲染对应看板/操作）。
> - **计时服务资源/计价**：通用资源模型 + 通用计价引擎（计费单位/递增/舍入/让利方向可配）。
> - **租户开通**：默认初始化模板（按业态）+ 可新增模板。
> - **预约迁移**：一阶段预约属二阶段，代码/库/表/数据全部迁移。
> - **报表**：JimuReport（积木报表）开源免费，Java 原生接入聚合读模型。
> - **税务**：首发不做税务相关。
> - **员工管理 + 业绩管理**：基本功能优先保障。

## 2. 愿景、目标与原则

第二阶段建设“多业态门店经营 SaaS 内核”，支持酒店、KTV、足浴和收银/零售经营闭环，并从第一天具备多租户、多组织、多门店、多国家地区、多时区和多币种的演进能力。

首发原则是“小而全”：不追求一次建设完整 ERP 或全渠道营销，而是保证从租户开通、门店经营、预订/开单、履约、收款、退款、交班日结到报表审计的业务闭环。

以下原则持续生效：

1. 统一交易，分业态履约；不建设四套相互复制的订单、支付和报表体系。
2. 多租户隔离、资金安全、隐私合规和审计可追溯是上线门槛，不作为后补功能。
3. 门店经营能力由后端权威校验；客户端看板和日历不决定资源占用、金额或权限。
4. 默认配置应让租户开箱即用；涉及真实资金、跨境、密钥、自动退款和高风险审批的能力默认关闭。
5. Gateway 只承担鉴权、路由、限流、审计等横切责任，不承担领域业务编排。
6. IM 与 SaaS 业务解耦：IM 聊天仅作为 C 端入口之一（授权登录 + 用户信息同步），SaaS 业务系统拥有独立账号与业务闭环，不依赖 IM 运行。
7. IM 与 SaaS 独立产品化：两者数据库独立、代码独立、独立部署、可独立销售；仅共享公共工程规范、技术框架与公共依赖（公共层），业务形态不耦合。部署可共用统一域名与网络环境。

## 3. 已确认决策总览

| 主题 | 已确认决策 |
| --- | --- |
| 经营模型 | 一个租户可跨国家、组织和门店经营；一期组织仅支持一层，不支持无限组织树。 |
| 数据库（SaaS 内部） | 共享数据库、严格行级租户隔离；不为每个租户建立独立数据库，预留未来路由抽象。 |
| 业态 | 首发业态为 **KTV**；酒店、足浴、普通收银/零售共用交易内核，作为后续演进。 |
| KTV（首发） | 支持包厢预订、开台、计时、加项、结台、现金结算与交班日结；不做酒水库存、最低消费。 |
| 酒店（后续） | 支持预订、散客入住、押金、续住、换房、钟点房、退房结算及押金抵扣/原路退还；非首发。 |
| 足浴（后续） | 支持项目、房间、技师排班/指派、服务计时、加钟与结单；不做技师提成；非首发。 |
| 首发区域 | 中国及东南亚；每个门店必须配置国家地区、时区、默认币种、语言、税率和营业日切点。 |
| 支付 | 默认支付为 **现金 + 储值币/代币（业务术语，默认展示名 A380币，租户可自定义）+ 积分**组合；支付宝、微信支付、Stripe（海外）均为可开关且**默认关闭**，不开通也能完整闭环。渠道按租户开放，租户自带商户号自行配置/测试，平台不代收不清分。支付渠道适配属通用支撑域。 |
| 订单 | 采用统一订单主表、统一资金模型和业态专属履约模型；预约保持独立生命周期。 |
| 权限 | 首发采用可演进 RBAC：多角色、作用域、服务端鉴权和审计；高风险动作结合审批。 |
| 会员 | 平台身份、平台积分、租户客户、租户会员、积分/权益/储值严格分层。 |
| 营销 | 平台运营、平台营销、租户营销是三个独立领域；交易优惠与运营触达分离。 |
| IM 与 SaaS | IM 与 SaaS 是两个独立产品/系统：数据库独立、代码独立、独立部署、可独立销售；仅共享公共工程规范/框架/依赖（公共层）。IM 聊天仅作为 C 端入口之一，通过授权登录（OAuth）+ 用户信息同步打通。 |
| 通用支撑域 | 跨业务通用运行能力（媒体、审核、邮件、短信、支付）独立成域（`common-services/`、`common-*`）；支付为域内多服务子域（下探一层：业务 + 渠道）。配置管理与审计统一进通用能力后台，按角色分配权限。 |
| 短信 | 短信能力开发好并预留待配置参数；后台可配置阿里云、腾讯云等国内及国外短信服务商（可开关）。 |

## 4. 领域边界

### 4.1 目标领域图

```text
平台治理
├─ 平台运营：租户生命周期、能力开通、审核、支持、审计
├─ 平台营销：线索、试用、套餐促销、平台积分/权益、平台触达
├─ 订阅与计费：后续独立设计，负责套餐、账单、平台优惠结算
└─ 身份与 IAM：账号认证、会话、用户角色、权限与数据范围

租户经营
├─ 租户与组织：Tenant、Organization、Store、商户主体、收银终端
├─ 目录与资源：商品服务、价格、房间/包厢/足浴房、技师、排班
├─ 预约与交易：预约、统一订单、业态履约（资金结算调用通用支撑域的支付域）
├─ 客户与会员：租户客户、等级、积分、权益、储值
└─ 租户营销：活动、优惠、券、会员运营、客户触达和效果统计

通用支撑域（跨业务通用运行能力，Common Services）
├─ 支付域：支付意图/退款/押金/班次/日结（业务） + 支付渠道（微信/支付宝/Stripe）
├─ 媒体域：媒体对象、上传会话、存储适配、访问授权
├─ 审核域：内容审核/安全
├─ 邮件域：邮件触达
└─ 短信域：短信触达（阿里云/腾讯云等可配置）
```

平台运营负责“租户是否可以使用何种平台能力”；平台营销负责“面向谁推广并提供什么增长激励”；租户营销负责“租户如何经营自己的客户”。三者可共用身份、同意管理、消息、审计和报表基础能力，但不共享业务对象的写入权限。

### 4.2 与现有仓库的关系

现有 `platform-order-service` 已拥有预约、门店、核销、积分协作和事件协作雏形。后续应保留其预约兼容契约，并将其逐步演进为交易相关能力的一部分；不得以新 SaaS 需求破坏已发布的预约接口与数据归属。

`im-admin-service` 继续是 IM 产品后台（积分/媒体/用户管理）的北向适配层，独立于 SaaS 后台。SaaS 后台由新增 `platform-admin-service` 承担，内部按权限区分平台运营后台与租户后台，不直接拥有或读写交易权威表。不得将管理端适配服务演变为交易、资金或资源领域的权威所有者。

IM 与 SaaS 解耦为两个独立产品：`im-user-service`、`im-message-service`、`im-conversation-service`、`im-access-ws` 属于 IM 产品域，只承载聊天/社交能力；SaaS 业务系统属于独立产品，拥有独立账号体系（新增 `platform-identity-service`，见 [SAAS_PLATFORM_02_SERVICE](SAAS_PLATFORM_02_SERVICE.md)）与独立业务闭环。两者数据库独立、代码独立、独立部署、可独立销售；公共工程规范、技术框架与公共依赖（`sdk/infrastructure`、`common`、`protocol-mq`）抽为公共结构，供两产品共用，业务形态不耦合。IM 仅作为 C 端入口之一，通过授权登录与用户信息同步打通，不作为 SaaS 账号权威或业务底座。现有 C 端预约属 SaaS 业务，其账号与数据归属随 SaaS 独立库迁移，C 端 App 同时持有 IM Token（聊天）与 SaaS Token（预约/交易）。

新增的租户/IAM、商户支付配置、资源履约、会员、营销等能力，应在领域映射完成后决定是否为现有服务扩展或新建独立领域。本文不预设 Java 模块名、数据库名、表前缀或字段名。

## 5. 租户、组织、门店与支付归属

```text
SaaS Platform
└─ Tenant
   ├─ Organization（品牌、集团、事业部）
   │  └─ Store（实际经营与收银地点）
   ├─ Legal Entity（签约、收款、结算主体）
   │  └─ Merchant Account（渠道商户账户）
   └─ IAM（用户、角色、授权范围）
```

关键约束：

- 所有租户经营事实均带 `tenant_id`；高频查询、唯一约束、缓存、对象存储路径、导出任务、异步消息与审计记录均继承租户上下文。
- `organization_id`、`store_id` 是权限和数据范围条件；门店只能归属一个组织。
- 门店固定配置 ISO 国家代码、IANA 时区、ISO 货币、语言、税务规则和营业日切点。
- 商户主体归属一个租户，可服务一个或多个门店；支付商户账户归属一个主体与一个渠道，密钥永不返回客户端。
- 收银终端必属一个门店；每笔收款关联终端与班次。

支付账户采用“主体级录入、门店级启用”。收款前，服务端按订单的租户、门店、币种、金额和业态，依次校验门店支付启用状态、商户账户状态、渠道国家/币种/金额/退款能力和终端支付方式，最终返回可展示且可发起的方式。前端展示不是支付授权。

### 5.1 门店业态与多业态可扩展

租户（Tenant）是**集团组织**：一个租户下可有一个或多个组织（品牌/集团/事业部），每个组织下多个门店；**每个门店绑定一种业态**（`business_type`），KTV 是首发业态之一，未来可增加酒店、足浴、按摩、超市等。

- **门店业态**：`tnt_store.business_type` 标识（`KTV/HOTEL/SPA/MASSAGE/RETAIL`...，可注册扩展）；一个门店一种业态；同一集团多业态 = 多个门店分别绑定不同业态。
- **统一 vs 专属**：统一订单主表、统一资金、统一会员/积分/储值（A380币）、统一营销、统一租户 IAM 跨业态复用；业态专属的履约状态机、资源类型、计价方案、目录模板独立（KTV 的 `ord_ktv_session` + `KTV_ROOM`/`KTV_SERVER`；酒店/足浴等各自专属）。
- **新增业态的扩展点（不改统一层）**：①登记 `business_type` 枚举与业态说明；②定义业态专属履约聚合（聚合根/状态机/表，如 `ord_<type>_session`）；③登记业态专属资源类型（`resource_type`）与计价方案字段；④提供业态专属目录/商品模板与 B 端页面/交互；⑤统一订单/资金/会员/营销/租户 IAM 不随业态新增而改动。
- **集团跨业态视角**：租户级报表按统一订单/资金维度跨业态汇总；业态专属资源/计价/履约数据按门店（业态）隔离。
- **业态扩展方式（决策）**：新增业态 = 代码（业态专属履约/资源/计价）+ 配置（`business_type` 登记），统一订单/资金/会员/营销/IAM 不随业态新增而改动；组织层级一期一层（租户→组织→门店），多层组织树后续演进。
- **`business_type` 枚举形态（决策）**：枚举值存 DB 枚举表（`tnt_business_type`，可配），每个业态的履约聚合/资源类型/计价方案在代码注册（新增业态写代码、不改统一层、不改 App 主体）；服务端白名单校验，防非法业态值。

支付宝、微信支付、Stripe 的实际可用性受商户主体、目标国家、币种和渠道能力限制。Stripe 首发定位为国际卡支付能力，不作为所有东南亚国家的通用本地支付能力。

## 6. 统一交易、资金与履约

### 6.1 交易模型

采用“统一订单主表 + 统一订单明细/资金模型 + 业态专属履约模型”。主订单仅表达稳定商业状态、金额汇总、门店、客户、币种、审计等公共事实；酒店入住、KTV 开台、足浴服务等专属状态留在各自履约模型中。

```text
统一订单
├─ 订单明细
├─ 支付意图与支付交易
├─ 退款交易
├─ 押金账本
├─ 酒店履约
├─ KTV 履约
├─ 足浴履约
└─ 预约关联
```

预约可独立创建、取消或标记未到店；到店后与正式订单关联或转化，不强行并入订单主生命周期。

统一订单商业状态为：`草稿 → 待支付/待到店 → 服务中 → 待结算 → 已完成`。异常分支为取消、作废及已完成后的部分/全额退款；退款不将订单回退为未完成。

金额、折扣、税费、已收金额和应退金额只由服务端根据价目快照、活动规则和资金记录计算，客户端不得传值决定最终金额。

### 6.2 资源占用

资源类型首发包含 **KTV 包厢**（房间、足浴房、技师为后续业态）。资源冲突必须由后端在事务中判定，同一资源的重叠时段只能存在一个有效占用。

- 酒店：可用 → 已预留 → 使用中 → 待清洁 → 可用。
- KTV：按时段预留，开台后使用中，结台后直接可用。
- 足浴房：开单占用，结单后直接可用。
- 技师：空闲 → 已预约 → 服务中 → 空闲；首发只记录排班、指派和时长。

### 6.3 支付、押金与退款

订单允许组合支付。支付、退款、押金和退押金都必须记录渠道交易号、金额、币种、汇率快照、操作者、收银终端、班次和审计轨迹。

酒店押金是订单下独立资金用途，不与房费混合：`收取 → 可用 → 抵扣或原路退还 → 已结清`。退房结算顺序为：计算应收 → 使用押金抵扣 → 支付差额或退还余额 → 固化账单、支付回调摘要与审计。

退款优先原支付渠道。渠道不支持时，只有具备财务权限的角色可登记线下退款。支付密钥仅由服务端加密托管，门店不可见。

## 7. RBAC、角色与高风险操作

首发采用 RBAC 作为主授权模型。用户可具有多条角色分配，每条角色具有租户、组织、门店或自身作用域；后端在当前登录上下文中校验权限和数据范围，客户端菜单与按钮控制仅用于体验。

首发预置角色（KTV 场景）：平台运营、平台营销、租户老板/总部运营（一个角色，租户级跨店权限）、门店店长、收银员、前台/预约、服务员、财务。平台运营与平台营销是独立角色与权限集合。房务为酒店场景角色，首发不启用。

高风险操作包括改价、整单优惠、作废、反结、线下退款、跨店操作及客户数据导出。它们必须包含权限点、数据范围、申请原因、操作者和审计记录；退款阈值、作废窗口和双人复核属于业务规则与审批流，不硬编码到角色中。

首发规则：收银员可收款、收押金并发起退款/作废申请；店长可审批本门店退款和作废；反结、线下退款、跨日修改由财务权限审批和复核。平台运营不查看商户交易正文或代替商户退款。

后续演进顺序：角色模板/继承、临时授权、可配置审批流，最后仅在确有需要的高风险场景引入 ABAC 条件。

## 8. 身份、客户与会员

### 8.1 账号与租户客户分层

SaaS 平台账号（可登录身份）和租户经营客户必须分离；IM 账号仅作为 C 端第三方登录入口（OAuth），不承载 SaaS 账号。

```text
SaaS 平台账号
├─ 登录标识（手机号、邮箱、IM 等第三方身份）
├─ 凭据、会话与最小个人资料
├─ IAM 授权关系
└─ 租户客户关系
   ├─ 租户客户档案
   ├─ 租户会员资格、等级、积分和权益
   └─ 租户储值与订单
```

SaaS 平台账号注册一次后可在不同租户消费，也可同时是某租户员工。租户只能看到当前租户内的客户档案、会员和交易，不能得知客户是否属于其他租户或其跨租户消费情况。

前台员工录入但未经客户本人验证码验证的手机号，只能形成租户内待认领档案，不能视作全局可登录账号。客户完成验证后才可关联全局身份。手机号、邮箱、证件等敏感数据应加密保存并使用规范化、不可逆检索摘要实现登录查找与唯一性校验。

平台级服务条款与账号安全授权、租户级隐私/履约通知授权、营销渠道授权必须分开记录。营销默认不订阅；跨国门店按当地最小采集、保存期限和跨境传输规则处理。

### 8.2 平台积分与租户会员

平台积分是平台营销领域的未来能力，独立于租户会员积分。租户及其门店不可见、不可读写、不可参与租户订单结算。首发只预留账号关联与领域边界，不建设平台积分的规则、运营页面或兑换能力。

租户会员归属租户经营领域。积分、权益、储值和订单都不得跨租户共享；每类资产可分别定义共享范围：

| 资产 | 可配置范围 | 安全默认值 |
| --- | --- | --- |
| 会员等级 | 全租户、组织、国家/地区、门店 | 同集团（租户）通用 |
| 积分 | 国家/地区、币种、组织、门店 | 同集团（租户）通用（按币种计划） |
| 权益 | 国家/地区、业态、门店、指定门店 | 同集团（租户）已启用门店 |
| 储值（储值币/代币） | 商户主体、币种、国家/地区、门店 | 同集团（租户）+ 同主体 + 同币种（跨币种关） |

积分发放、权益领取和订单优惠应保留规则快照。门店停用或不再满足范围条件后自动不可使用。

> 共享默认「集团级（租户）通用」：会员/积分/权益/储值在同一租户（集团）内跨业态门店通用，可配门店范围；储值跨币种仍默认关闭。

### 8.3 储值与跨币种

储值等同现金负债，必须以不可篡改的资金账本表达充值、消费、退款、冻结和冲正，不得直接修改余额。储值账户至少按客户、租户、商户主体和币种隔离；不同币种是不同账户。

首发只允许同币种储值消费。跨币种或跨国抵扣虽然预留为平台能力，但默认关闭；不得仅因当地可接受某种现金而允许系统内兑换或清算。启用具体国家/地区和币种对前，必须具备资金发行/结算主体、适用合规能力或合作方、KYC、交易限额、制裁及可疑交易筛查、汇率报价、费用快照、人工复核和完整审计。

## 9. 营销领域

### 9.1 三层营销边界

```text
平台营销
├─ B2B 获客：线索、试用、套餐优惠、租户转化
├─ 平台租户运营：产品公告、续费/活动触达
└─ 平台用户运营：未来的平台积分、平台权益、平台触达

租户营销
├─ 交易促销：折扣、满减、套餐、时段价、优惠券
├─ 会员运营：等级、积分、储值赠送、权益
├─ 客户增长：拉新、邀新、复购活动
└─ 客户触达：站内信、短信、邮件、第三方消息渠道
```

平台营销不等于平台运营。平台运营管理租户生命周期、产品能力、审核和支持；平台营销管理增长活动、目标受众、激励、触达和转化。平台面向租户客户的营销必须有独立的平台营销授权与合同边界，不能复用租户经营数据。

### 9.2 交易优惠与运营触达

交易优惠和运营触达是不同能力：

- 交易优惠影响订单金额，须由服务端在结算时校验、锁定、核销/释放，并固化规则、优惠金额与资金承担方快照。
- 运营触达负责受众筛选、消息编排、渠道发送、频控、退订和效果统计，只能向已同意该渠道营销的受众发送。

平台补贴租户活动时，必须记录承担方、适用租户/门店、预算和结算方式，不得与租户自有折扣混淆。

### 9.3 首发与预留

首发租户营销提供优惠券、固定折扣、满减、会员专享价，以及手工发券、订单后发券、注册/首次消费发券。规则支持有效期、总量、每人限领/限用、商品服务范围、业态及门店范围，并提供发放、领取、使用、核销和优惠成本基础统计。

首发不做复杂人群圈选、自动化旅程、A/B 测试、智能推荐或裂变体系。营销领域预留活动、规则、受众、发放物、适用范围、资金承担方、预算、触达任务、归因和效果统计等对象，以支持后续演进。

## 10. 各端首发定位

| 端 | 首发定位 |
| --- | --- |
| 平台 PC（SaaS 平台运营后台） | 租户、平台运营、平台营销、国家/币种、渠道能力、平台审计和支持。 |
| 商户 PC 管理端（SaaS 租户后台） | 工作台、订单预约、资源、商品服务、会员、资金、日结、报表、员工角色、审计和门店配置。 |
| 收银端 | 开班、包厢看板、快速开台、订单操作、收款、退款申请、查询和交班。 |
| 移动 App | 门店移动执行与店长经营看板：待办、包厢状态、开台/计时/加项/结台执行、简易开台/预订、审批和经营摘要。 |

移动 App 首发不承担价格体系、支付密钥、角色配置、复杂报表导出和批量资源配置；这些能力保留在 PC 管理端。

**员工管理与业绩（首发优先）**：员工（含服务人员/收银/店长等）的档案、角色分配、班次、业绩（开单/服务/收款/加项提成绩效口径）是基本功能，首发优先保障；业绩数据统一落统一订单/资金维度，跨业态可汇总。

**租户开通模板**：平台开通租户时按业态提供「默认初始化模板」（组织/首门店/角色权限/资源/计价方案/收银班次等），并支持新增自定义模板；新业态落地时配一套默认模板。

## 11. 开箱即用初始化

平台人工开通租户后，系统自动初始化默认组织、首门店、基础角色、权限模板、收银班次、订单状态、基础价目/税率待确认项、会员基础等级、首门店币种对应的标准积分计划、权益模板、同主体同币种储值使用范围及必要审计能力。

默认启用可安全使用的基础能力：现金收银、同币种会员积分/权益、基础开单和结算。支付生产密钥、跨主体/跨币种/跨国储值、自动退款、平台积分运营及高风险审批自动执行均默认关闭，需租户或平台按权限显式配置与审核。

新增国家或不同币种门店时，系统应根据国家地区模板预填币种、时区、语言、营业日切点和税务配置，并要求负责人确认；不同币种门店自动拥有独立标准积分计划，租户可在符合规则后配置共享。

## 12. 首发明确不包含

- 复杂 ERP、采购与供应链。
- 多法人结算、集团内部结算、多级加盟分润、佣金/技师提成。
- OTA/渠道直连、跨境电商、完整 CRM 自动化、多国电子发票认证。
- 所有国家本地支付渠道、平台代收/清分、跨币种储值清算。
- 自助 SaaS 注册、自动扣费与完整订阅计费。
- 平台积分规则、平台消费者活动与平台用户运营自动化。
- 复杂营销分群、可视化营销旅程、A/B 测试、智能推荐和裂变体系。

不包含不等于没有边界：上述能力必须预留领域接口、数据归属与审计扩展点，但不得阻断首发门店经营闭环。

## 13. 上线基线与后续详细设计

上线前必须满足：租户隔离、权限数据范围校验、支付密钥加密、支付与退款审计、资源并发占用控制、金额服务端计算、敏感数据保护、删除/导出流程、异步消息租户上下文继承和基础备份恢复验证。

后续方案按以下顺序推进：

1. 对齐现有领域与契约，完成租户、组织、门店、身份/IAM 的详细边界和迁移策略。
2. 细化统一订单公共状态与金额字段，以及 KTV 履约状态机（酒店、足浴后续）。
3. 细化支付商户配置、支付适配、押金账本、退款/反结、交班日结与对账。
4. 细化客户身份、租户客户、会员、积分、权益、储值账本和隐私同意。
5. 细化租户营销首发规则与订单优惠核销契约；平台营销、平台运营、订阅计费分别形成独立方案。
6. 分别形成 PC 管理端、收银端、移动 App、数据迁移、测试和部署实施方案。

## 14. 变更清单

本方案进入实施前，后续专项方案必须明确并同步以下内容：

- 单元、集成、并发、权限隔离、资金一致性、跨时区/币种和端到端测试。
- 灰度、监控、告警、备份恢复、数据导出/删除和安全审计部署配置。

### 15.1 参考项目使用原则

1. 核心领域模型以本方案和现有仓库契约为准，不因参考项目的表结构、状态值或服务划分直接改写。
2. 参考代码进入仓库前必须记录来源、版本、许可证、修改范围、版权声明和对应 SBOM 条目。
3. LGPL、GPL、AGPL、OSL 等许可证不能简单按“允许商用”处理；代码复制、链接、网络提供、修改发布和插件扩展分别进行合规评估。
4. 优先采用 Apache 2.0、MIT、BSD 等边界清晰的基础设施依赖；业务核心尽量自研，避免形成多套订单、客户、权限和账务事实。
5. OpenIM 仅作为即时通信基础设施参考。SaaS 领域的租户、组织、门店、会员、营销和交易数据必须由对应领域服务拥有。

| Admin 同时服务平台和租户 | 已覆盖职责方向 | 平台 PC、商户 PC、平台运营/营销、租户老板、总部、店长、收银、财务角色与菜单 | 平台后台与租户后台的路由、上下文、菜单权限、服务端接口归属，以及现有 `im-admin-service` 的演进方案 |

因此，当前方案已经覆盖第二阶段最初提出的目标，尤其覆盖了“现有 C 端 App 之外新增 B 端 App”和“Admin 同时服务平台与租户”这两个容易遗漏的要求。

### 16.2 当前尚未达到的程度

当前文档仍是业务与领域基线，尚未达到可以直接拆分代码任务的实施深度。以下内容必须在进入开发前形成专项设计：

1. 现有仓库领域、数据库、认证模型和接口契约的盘点，以及兼容/迁移边界。
2. 租户、组织、门店、员工、客户和平台账号的实体关系、唯一键、租户过滤和初始化事务。
3. `admin` 平台上下文与租户上下文的登录、切换、路由、菜单和 API 鉴权方案。
4. B 端 App 的工程形态、接口清单、权限矩阵、弱网/离线策略及设备能力边界。
5. 统一订单公共字段、酒店/KTV/足浴履约字段、支付/退款/押金账本和完整状态机。
6. 价格、优惠、积分、储值和退款之间的金额计算及回滚规则。
7. Flyway、事件、缓存、对象存储、导出任务和 MQ 消费的租户隔离实现。
8. 测试数据、并发占用、支付回调、权限穿透、跨时区/币种和端到端验收方案。

### 16.3 进入实施层面的判断

可以进入实施层面，但应以专项设计顺序推进，而不是直接按本文件编写全部代码。建议第一批先冻结“SaaS 账号/IM 入口边界 + 租户/IAM/后台上下文 + 统一订单公共模型 + KTV 履约状态机”，再并行展开 B 端 App 和支付资金方案。

首批实施的完成定义应包括：

- 现有 C 端预约能力继续兼容，且不破坏既有 `user`、`order`、`admin` 契约；
- 平台管理员和租户管理员能够在不同数据范围内登录、切换和操作；
- KTV 完成至少一条从开台/履约到结算的后端闭环（酒店、足浴后续）；
- B 端 App 能完成门店登录、待办/资源查看、基本业务执行和权限校验；
- 所有新业务数据具备租户上下文，支付、退款和高风险动作具备审计与幂等。

## 17. 一阶段基础上的增量演进原则

二阶段不是重新建设一套与当前系统并行的产品，而是在一阶段当前版本的能力、数据和客户端契约之上持续迭代。所有详细方案必须同时回答“新增能力如何落地”和“现有能力如何保持可用”两个问题。

### 17.1 兼容优先

- 现有 C 端 App、预约、账号登录、消息和既有后台能力在没有明确迁移方案前不得破坏。
- 已发布的 REST 路径、请求字段、响应字段、状态编码和错误语义默认保持兼容；需要变更时采用版本化或兼容适配层。
- 现有 `platform-order-service`、`im-user-service`、`im-admin-service` 和 Gateway 的权威边界先盘点再调整，不能通过新功能绕开已有服务契约直接读写其数据库。
- 一阶段已有数据继续可查询、可审计；新增租户字段、客户关系或订单关联必须提供默认迁移值和回填策略。

### 17.2 逐域扩展

二阶段按领域逐步扩展，不采用一次性全量重写：

1. 先建立租户/IAM 上下文和兼容适配，使现有用户与管理员能够继续访问原有功能。
2. 在预约和门店基础上扩展资源、统一订单和业态履约；已有预约先保持独立生命周期。
3. 在统一订单稳定后接入支付、退款、押金、交班和日结，不把资金事实留在前端或管理适配服务。
4. 再扩展租户客户、会员、营销和 B 端 App；每个领域以事件或内部契约与既有服务协作。

每个领域详细方案必须声明：现有权威服务、目标权威服务、兼容期间的读写路径、数据迁移批次、切换条件、回滚方式和回归测试范围。

### 17.3 数据与发布安全

- 数据库变更只使用可回滚策略可验证的前向迁移；历史 Flyway 脚本不可修改。
- 新增能力优先使用开关、租户级启用和门店级灰度，未启用租户不改变现有业务行为。
- 需要改变数据归属时，先建立新模型与回填校验，再切换读路径，最后停止旧写路径；禁止无审计的直接搬表或删除旧字段。
- 跨服务迁移期间，事件、幂等键、重试和补偿必须可追踪；资金和订单事实不采用不可验证的双写。
- 每个实施批次都必须包含旧功能回归、权限隔离、数据一致性和端到端客户端验证，而不只验证新接口。

### 17.4 二阶段完成标准

二阶段不是以“新模块编译通过”为完成条件，而是同时满足：

- 一阶段已有 C 端和后台核心流程继续可用；
- 新增 SaaS 租户上下文不会造成跨租户数据泄露；
- KTV 至少有一条可实际结算的闭环（酒店、足浴为后续演进，不阻断 KTV 首发）；
- B 端 App 和租户后台能够在既定权限范围内完成门店运营；
- 新旧数据、订单、支付、消息和审计链路可追踪、可回归、可回滚。
