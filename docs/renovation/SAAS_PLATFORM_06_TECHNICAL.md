# SaaS 多业态特殊技术方案

> **变更记录（v2）**：首发收敛为 KTV，新增 KTV 计时计费规则（§4.3）；酒店押金、足浴排班相关并发规则后置。

## 1. 目标与适用范围

本文解决业务方案中不能仅靠普通 CRUD 实现的技术问题，作为后端、Admin 和 B 端 App 的统一实施约束。本文不替代支付渠道的合规审核和安全评估；真实上线前必须以目标国家、商户主体和渠道协议为准。

## 2. 多租户隔离

### 2.1 请求链路

```text
Gateway 鉴权
  → 校验 SaaS 账号 Token
  → 校验 tenantContextToken
  → 注入 TenantContext（tenantId、orgId、storeId、accountId、permissions、authVersion）
  → 领域服务再次校验权限和数据范围
  → Repository 自动附加 tenant_id
```

`TenantContext` 只允许从签名 Token 和 IAM 查询生成。禁止从 URL、Header 明文或请求体直接信任租户 ID。平台跨租户操作必须使用专用平台权限、临时授权、原因、有效期和审计记录。

### 2.2 数据访问防穿透

Repository/Mapper 提供带上下文的标准查询入口；业务代码不得拼接无租户条件 SQL。开发环境启用 SQL 检查器：租户业务表的 `SELECT/UPDATE/DELETE` 缺少 `tenant_id` 时失败（落地为 `scripts/validate/validate-tenant-sql.ps1` + MyBatis 租户拦截器，并入统一校验入口与 CI 门禁）。批处理、MQ 消费、导出和缓存读写必须显式创建上下文。

每个租户至少执行以下自动化测试：

- 租户 A 的 ID 查询不能读到租户 B；
- 直接修改请求体 `tenantId` 不改变实际范围；
- 门店角色不能读取其他门店；
- 导出、异步任务和缓存 key 不能越租户；
- 平台临时授权过期后立即拒绝。

## 3. 资源并发占用

### 3.1 预留与确认

资源服务使用数据库事务完成：

1. 按 `tenant_id + resource_id` 查询有效占用，使用 `SELECT ... FOR UPDATE` 或资源锁行。
2. 校验时间区间重叠、资源状态、门店和业务权限。
3. 创建 `HELD` 占用，设置 `hold_expires_at`；支付/履约确认后转 `RESERVED` 或 `IN_USE`。
4. 事务提交后发送 `resource.occupied` Outbox 事件。

同一资源只能串行处理。不能依赖 Redis 锁作为最终事实；Redis 锁只能降低冲突，数据库锁和唯一约束才是最终防线。不同数据库实例通过同一资源权威库路由。

### 3.2 释放与超时

定时任务每分钟扫描过期 `HELD`，使用版本条件释放；任务必须幂等。订单取消、支付失败、退款成功和结台/退房分别触发释放命令，重复释放返回成功但不产生第二条事实。

酒店退房后房间进入 `待清洁`；KTV 结台和足浴结单按规则直接释放。资源状态变化必须带 `stateVersion`，客户端看板发现版本落后时重新拉取。

## 4. 订单状态机与金额一致性

### 4.1 状态变更

订单服务维护显式状态转换表，任何命令先加载当前状态、权限、版本和业务规则：

```text
DRAFT → WAITING_PAYMENT / WAITING_ARRIVAL / CANCELLED
WAITING_PAYMENT → SERVING / CANCELLED
WAITING_ARRIVAL → SERVING / CANCELLED / NO_SHOW
SERVING → WAITING_SETTLEMENT / VOIDED
WAITING_SETTLEMENT → COMPLETED / VOIDED
COMPLETED → PARTIAL_REFUNDED / REFUNDED
```

版本使用乐观锁 `version`；更新条件为 `id + tenant_id + version`，影响行数为 0 返回 `ORDER_VERSION_CONFLICT`。高风险作废、反结和退款不直接绕过审批状态。

### 4.2 金额计算

结算服务依次执行：

1. 读取价目、业态计时规则、门店税率和活动规则快照；
2. 计算明细原价、数量、折扣、税费和附加费；
3. 校验积分、优惠券、储值和押金可用范围；
4. 按固定优先级应用优惠并舍入；
5. 写入订单金额快照，生成应付和可退款金额；
6. 返回明细、币种、税费、优惠承担方和规则版本。

客户端只能提交选择项和 `expectedVersion`，不能提交最终金额、税费、汇率或折扣结果。已完成订单的价格规则变化不影响历史快照。

### 4.3 KTV 计时计费规则（首发）

KTV 履约的计时计费是首发核心，由后端在结台时结算：

1. **计费单位**：按门店配置 `billing_unit`（`HOUR/HALF_HOUR/PACKAGE`）取整；不足一个计费单位按门店舍入规则（向上取整/按比例）处理。
2. **起算时间**：`billing_start_at` = 开台时间 + `free_wait_minutes`（免费等待，默认 0）；开台即计费时二者相同。
3. **暂停不计费**：`pause` 期间累计 `paused_seconds`；结台计费时长 = 结台时间 − 起算时间 − 暂停时长。
4. **超时加价**：超出预订时段或门店标准的时长按 `overtime_rate`（默认 1.0）乘超时部分；规则固化在 `billing_rule_snapshot_json`。
5. **加项叠加**：加项商品/服务按订单明细独立计价，不与计时费合并；优惠按 §7.2 优先级应用。
6. **金额快照**：结台时固化计费单位、单价、计费时长、暂停时长、超时费率与各明细金额；后续改价不影响已结订单。

计时状态：`RESERVED → OPEN → PAUSED(可选) → CLOSED`；暂停/恢复不改变起算时间，只累计暂停时长；计时不可倒退，任何命令校验 `version` 乐观锁。

> **通用计价引擎（决策 D-5/6）**：上述「计费单位/递增粒度/舍入方向/让利」抽成通用计时计价引擎，KTV 包厢与服务人员先验证；未来酒店房费、足浴/按摩技师计时复用同一引擎，业态只提供规则快照，不各造一套计价。**KTV 阶段暂不独立引擎化**（用计价方案 + 规则快照 schema 承载），多业态复用时再抽独立引擎与契约，避免过早抽象。

## 5. 支付与退款一致性

### 5.1 支付意图

支付命令使用 `tenantId + orderId + idempotencyKey` 唯一。创建前锁定订单版本并校验可支付金额；支付意图固化商户主体、渠道、币种、费率和能力快照。支付中的订单禁止创建第二个相同用途的意图。

渠道返回二维码/跳转信息后，客户端只展示服务端返回值；客户端不持有密钥。支付结果以异步回调或服务端查询为准，前端“支付成功”仅是待确认状态。

### 5.2 回调处理

1. 验证渠道签名、商户账户、环境和回调时间窗口。
2. 以渠道交易号和回调摘要做幂等判断。
3. 锁定支付意图，验证金额、币种和订单归属。
4. 只允许合法状态转换；已成功不被失败覆盖。
5. 写支付交易、订单支付汇总和 Outbox，同一事务提交。
6. 返回渠道要求的确认响应；异步通知失败由 Relay 重试。

完整回调正文只做加密/受限保存或摘要保存，日志禁止输出密钥、卡号和签名原文。

### 5.3 退款与押金

退款先创建申请，不改变原订单资金事实；审批成功后支付服务按原 `merchant_account_id + provider_transaction_id` 发起退款。渠道不支持时，财务登记线下退款并关联凭证。

押金抵扣是账本 `APPLY`，不是删除充值流水。退押金是 `REFUND`，失败可重试，成功后不可再次退款；所有冲正追加 `REVERSE` 流水。

## 6. 跨币种与反洗钱风控

首发只允许同币种储值消费。跨币种能力采用配置走廊：`sourceCountry + sourceCurrency + targetCountry + targetCurrency + legalEntity + channel`。

启用前检查：

- 商户主体和收款/结算资格有效；
- 目标国家与渠道支持该币种对；
- 客户身份、交易限额、频率和累计金额满足规则；
- 制裁、黑名单、异常设备和可疑交易筛查通过；
- 汇率报价未过期，费用和舍入规则明确；
- 退款路径与原资金来源一致。

每笔兑换保存 `fx_quote_id`、来源、报价时点、有效期、原币金额、目标币金额、手续费、规则版本和风控结果。风控拒绝时不创建扣款或兑换流水；高风险只允许进入人工复核，不允许客户端重试绕过。

## 7. 会员、优惠和账本规则

### 7.1 积分

积分发放默认按租户币种计划计算；押金、充值、退款和被冲正订单不自动赚取积分。订单完成后发放，退款/作废按规则产生反向流水。积分抵扣先冻结，结算成功后扣除，结算失败释放冻结。

### 7.2 优惠叠加

首发固定优先级：

```text
门店/商品特价
  → 会员价
  → 活动折扣/满减（择一）
  → 优惠券
  → 积分抵扣
  → 储值币/代币抵扣应付金额
  → 现金补差额
```

同一订单默认不叠加同类优惠；活动可通过规则明确允许例外。报价生成 `quoteId` 和过期时间，结算时重新校验并固化规则快照。

> **组合收款舍入口径（决策）**：金额全程最小货币单位整数运算；抵扣顺序固定「优惠 → 积分 → 储值币/代币 → 现金补差额」；舍入让利消费者（抹零向下）；储值/积分抵扣前校验余额，不足则部分抵扣或提示；现金找零按最小单位。

### 7.3 储值

储值账户按租户、客户、商户主体和币种隔离；余额不足、主体不匹配、币种不匹配、门店不在共享范围时拒绝。充值、消费、退款和冻结均使用账本幂等命令，禁止直接 UPDATE 可用余额绕过流水。

## 8. Outbox、MQ 与最终一致性

业务事实和 Outbox 必须在同一个 MySQL 事务提交。Relay 使用状态 `PENDING → PUBLISHED/FAILED`、指数退避和最大重试次数；超过次数进入死信并告警。

消费者以 `eventId` 建立消费去重表或业务唯一键。通知、报表、搜索和缓存是最终一致投影，不得作为订单、支付、资源的权威事实。事件载荷最小化，带租户上下文但不带敏感原文。

## 9. 缓存、限流与任务

- Redis 只缓存菜单权限摘要、资源看板短期投影、幂等结果和分布式协调信息；设置租户前缀和版本。
- 权限/上下文缓存按 `authorizationVersion` 失效；角色变更不能等待自然 TTL。
- 资源状态缓存 TTL 不超过 30 秒，写操作后主动失效；读到旧版本必须回源。
- **限流/熔断采用「Redis + Sentinel 互补」方案**：
  - **限流（全局精确）**：Gateway 按账号、租户、IP、接口多维限流由 **Redis** 承担（key 化计数器，跨实例全局精确）；支付、登录、验证码、导出用更低阈值。保留现有 Redis Lua 脚本或迁移 Redisson RateLimiter。
  - **熔断降级（Sentinel）**：服务调用熔断（慢调用比例/异常比例/异常数）、降级、单机 QPS 流控兜底、系统自适应保护，由 **Sentinel** 承担（`spring-cloud-starter-alibaba-sentinel`）。
  - **规则管理**：Sentinel 规则接 **Nacos** 配置中心（动态规则 + 持久化），配合 Sentinel Dashboard；版本由 Spring Cloud Alibaba 2025.1.0.0 BOM 托管（Sentinel 1.8.x + Nacos 3.x）。
  - **职责边界**：Redis 管「全局多维计数限流」，Sentinel 管「熔断降级 + 单机流控 + 可观测」，互不替代，避免集群流控 Token Server 的部署复杂度。
- 定时任务采用租约/分片，任务执行携带租户上下文；账单、过期占用、优惠券过期、支付查询、日结提醒和 Outbox 重试必须幂等。

## 10. Admin 与 B App 安全

- Admin 平台操作和租户操作使用不同权限码、菜单和数据范围；平台运营不读取租户交易正文。
- B App 不存支付密钥，不允许离线资金操作，不允许通过客户端参数扩大门店范围。
- 敏感字段加密，密钥由受管 KMS/Secret 注入；日志只保留摘要、请求 ID、业务 ID 和审计 ID。
- 任何客户搜索只在当前租户范围进行；跨租户关联需本人授权和平台合规流程。
- 导出任务先创建授权快照，生成短期下载地址，过期自动失效，下载和分享均记审计。

## 11. 迁移、灰度与回滚

### 11.1 迁移策略

采用 Expand → Backfill → Verify → Switch → Contract：

1. 新增表/字段和兼容读模型，不删除旧字段。
2. 按租户批量回填，记录批次、数量、失败项和校验摘要。
3. 对账旧读与新读，差异进入人工处理队列。
4. 通过租户/门店开关切换新读写，观察指标。
5. 稳定后停止旧写入，保留只读窗口，再在单独迁移中清理。

绝不在同一批次进行不可逆删除、跨库隐式双写或没有备份的资金迁移。

### 11.2 灰度指标

监控租户隔离拒绝率、订单版本冲突率、资源冲突率、支付回调成功率、重复幂等命中率、退款延迟、Outbox 堵塞、API p95、B App 关键操作失败率和旧 C 端回归错误。指标标签只能使用有限集合的服务、接口、状态、渠道、业态和环境；租户/门店/订单/用户/请求 ID 只写日志、审计和 Trace，不作为指标标签。

### 11.3 回滚

应用回滚优先于数据回滚：停止灰度、关闭 feature flag、恢复上一版本制品和配置。数据仅在已验证备份和停写窗口下恢复；Flyway 不回改历史脚本，使用追加修复迁移。

## 12. 可观测性与故障处理

每条请求、事件、支付、订单和审计记录关联 `requestId`、`traceId`、`tenantId`（可脱敏）、`storeId`、`operatorId` 和 `idempotencyKey`。这些标识只用于日志、Trace 和受控审计查询，不作为指标标签；指标不暴露客户 PII。

必须告警：跨租户校验异常、支付签名失败、支付状态长期 PROCESSING、退款失败、账本不平、资源锁超时、Outbox 死信、数据库迁移失败和审计写入失败。资金/审计写入失败时宁可拒绝业务，也不能静默成功。

## 13. 特殊方案验收

- [ ] 两租户并发读取、写入、导出、MQ 消费和缓存验证无越权。
- [ ] 同一包厢并发开台只成功一次（房间/技师后续）。
- [ ] 同一支付/退款/押金命令重复 10 次只产生一笔资金事实。
- [ ] 渠道回调乱序、重复、金额不一致均不破坏已完成状态。
- [ ] 订单结算、优惠、积分、储值和押金失败可恢复且账本平衡。
- [ ] 跨币种未启用时所有入口统一拒绝；启用走廊后保存完整报价和风控快照。
- [ ] Redis、MQ、支付渠道短暂不可用时不产生虚假成功。
- [ ] 租户切换、角色变更和 Token 过期能立即阻断旧上下文。
- [ ] 扩展迁移、回填、切换和应用回滚完成演练。
