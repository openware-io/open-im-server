# DDD 微服务软件工程规范纲要

[中文](00_DDD_MICROSERVICE_SOFTWARE_ENGINEERING_OUTLINE.md) | [English](00_DDD_MICROSERVICE_SOFTWARE_ENGINEERING_OUTLINE.en.md)

## 目标

软件工程规范由可复用的规则体系与项目专属的实施方案组成。二者必须分离：规范回答“长期应当如何做”，方案回答“当前工程如何从现状达到规范”。

## 术语与前置假设

| 术语 | 定义 |
| --- | --- |
| 通用规范 | 可跨项目复用的工程约束：原则、术语、模板、允许/禁止项、门禁、验收标准与抽象案例。 |
| 项目工程规则 | 某项目选择并启用的规范集合：生效清单、项目级例外、环境基线与责任人。 |
| 改造方案 | 从现状到目标的迁移计划：现状、差距、模块清单、批次、风险、兼容与回滚。 |
| 架构决策记录 | 需要长期保留理由的关键决策：背景、备选、决策、后果与复审条件。 |
| 服务文档 | 单个服务的运行与边界说明：职责、接口、依赖、数据所有权、配置与演练方式。 |
| 最小模板 | 每份通用规范必须包含的七个部分（见本文"规范文档最小模板"）。 |

**前置假设**：规范与方案分属不同文档层级、可被独立评审；规范不携带项目专属内容；门禁可脚本化执行。

```text
通用工程规范
├── 设计思想与架构规范
├── 工程实现规范
├── 工具与开发效能规范
├── 质量、安全与可靠性规范
└── 交付与运维规范

项目专属材料
├── 现状评估
├── 改造方案与批次计划
├── 架构决策记录
└── 验收证据与复盘
```

## 文档分层

| 类型 | 定义 | 内容边界 | 变更频率 |
| --- | --- | --- | --- |
| 通用规范 | 可跨项目复用的工程约束 | 原则、术语、模板、允许/禁止项、门禁、验收标准、抽象案例 | 低 |
| 项目工程规则 | 某项目选择并启用的规范集合 | 生效规范清单、项目级例外、环境基线、责任人 | 中 |
| 改造方案 | 当前项目从现状迁移至目标的计划 | 现状、差距、模块清单、批次、风险、兼容与回滚 | 高 |
| 架构决策记录 | 需要长期保留理由的关键决策 | 背景、备选方案、决策、后果、复审条件 | 中 |
| 服务文档 | 单个服务的运行和边界说明 | 职责、接口、依赖、数据所有权、配置、演练方式 | 中 |

- 规范不得包含项目模块名称、存量缺陷、未完成事项或迁移顺序。
- 改造方案不得重写规范正文；它必须引用规范条目，并把每个偏差转化为范围明确、可验证、可回滚的工作项。
- 工程规则可以选择性启用通用规范，但不能悄然修改通用规范的语义；项目例外必须有期限、理由、负责人和退出条件。
- 案例可出现在规范中，但必须标记为“示例”，且不构成强制的目录、命名或技术选型。
- 规范文档名称以两位层级序号开头：`00` 为总纲，`10` 至 `19` 为设计思想与架构，`20` 至 `29` 为工程实现，`30` 至 `39` 为工具与开发效能，`40` 至 `49` 为质量、安全与可靠性，`50` 至 `59` 为交付与运维；同一层级按依赖和阅读顺序编号。
- 文档中引用仓库内其他文档、规范、服务说明、脚本或目录时，必须使用以当前文档为基准的可跳转相对 Markdown 链接，禁止仅以反引号包裹路径；无法跳转的纯文本路径只可用于命令、配置值和代码示例。

## 标准建设优先级

规范先行不等于一次性写完全部文档。按对架构约束和后续改造的影响排序：

1. 统一规范治理边界：规范、项目规则、改造方案和架构决策记录分离。
2. 固化设计边界：DDD、微服务边界、数据所有权、事件与一致性。
3. 固化工程边界：Maven、目录、对象隔离、MapStruct、配置和数据库迁移。
4. 固化质量基线：Java 代码、测试、可观测性、安全、可靠性与性能。
5. 固化交付闭环：门禁、CI/CD、发布、运行手册、事故复盘和文档治理。

## 规范文档最小模板

每份通用规范必须至少包含：

1. 目标、适用范围与非目标。
2. 术语和前置假设。
3. 原则、允许项、禁止项与例外机制。
4. 推荐模板或抽象示例，并明确案例不是强制命名。
5. 可自动化的门禁规则与人工评审检查项。
6. 可验证的验收标准。
7. 与其他规范、项目规则、改造方案和架构决策记录的关系。

## 项目采用流程

1. 选择并冻结适用的通用规范版本。
2. 编写项目工程规则，明确启用项、项目基线和暂时例外。
3. 完成现状评估，按规范条目建立偏差清单。
4. 单独编写改造方案，定义批次、兼容策略、数据迁移、风险、回滚与验收。
5. 先实现可自动化的门禁，再按依赖顺序改造工程。
6. 每批改造完成后沉淀可复用经验，更新规范、案例或门禁；项目特有内容保留在方案与决策记录中。

## 原则与允许禁止项

**原则**：
1. **分层不混写**：规范、项目规则、改造方案、决策记录、服务文档各司其职。
2. **规范先行**：先固化可自动化的门禁，再按依赖顺序改造工程。
3. **可复用优先**：项目特有内容一律留在方案与决策记录，不进规范正文。
4. **案例不等于强制**：案例仅说明规则的应用方式，不构成命名或选型要求。

**禁止**：
- 在规范中写入项目模块名称、存量缺陷、未完成事项或迁移顺序；
- 以"例外"长期豁免规范语义（例外必须有期限、理由、负责人与退出条件）；
- 用引用代替可跳转链接（引用仓库内文档须用相对 Markdown 链接，路径不得仅以反引号包裹）；
- 未经评审确认即执行涉及密钥轮换、数据库迁移、内部协议或发布门禁的变更。

**允许**：
- 项目规则选择性启用通用规范；
- 规范中出现标记为"示例"的抽象案例；
- 服务文档按项目实际补充运行细节。

## 门禁与人工检查项

**可自动化**：

| 门禁 | 判据 |
| --- | --- |
| 最小模板完整 | `docs/standards/*.md` 每份含七项必需部分（见下节） |
| 规范不含项目内容 | 规范层不出现仓库模块名、绝对本地路径、未完成事项占位符 |
| 文档可达 | 每份规范可从根 README 或索引到达 |
| 链接可跳转 | 仓库内引用使用相对 Markdown 链接且目标存在 |

**人工检查项**：
1. 新规范是否声明所属层级、范围与非目标。
2. 项目特有决策是否留在方案/决策记录，而非渗入规范。
3. 例外是否写明期限、理由、负责人与退出条件。

## 可验证的验收标准

| # | 判据 | 证据形式 |
| --- | --- | --- |
| 1 | 项目采用的每份规范都具备七项必需部分 | 规范治理门禁通过 |
| 2 | 规范层无项目模块名、绝对路径与未完成事项占位符 | 同上 |
| 3 | 每份规范都可从索引到达，且内部引用可跳转 | 文档链接门禁通过 |
| 4 | 项目工程规则列出启用清单、基线与例外（含退出条件） | 规则文档审查 |
| 5 | 改造方案以规范条目为依据，并给出可验证、可回滚的工作项 | 方案评审记录 |

**完成定义**：上表逐项有可复现证据，且统一工程校验入口在该范围退出码为 0。
