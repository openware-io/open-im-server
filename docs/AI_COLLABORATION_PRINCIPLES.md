# Karpathy 启发的 AI 协作指南

> 参考来源：<https://github.com/multica-ai/andrej-karpathy-skills>
>
> 本文件保留核心协作原则，并与本项目工程规范共同使用。

本指南用于改善 AI 与自动化改码行为，重点减少错误假设、无关改动、过度设计和未验证交付。

**权衡说明：**本指南偏向“谨慎优先于速度”。对于明显的一行修改或拼写修复，可以按风险裁剪流程，不必机械执行全部步骤。

## 问题来源

LLM 编码常见问题包括：

- 模型替代工程师做出错误假设，并沿着错误前提继续执行而不主动检查。
- 模型不管理自身困惑，不主动澄清、不呈现矛盾，也不展示权衡。
- 模型容易过度复杂化代码和 API，堆砌抽象、不清理死代码，将本可用 100 行解决的问题膨胀到 1000 行。
- 模型有时会改动或删除未充分理解的代码和注释，即使这些内容与当前任务无关。

## 解决方案

四个原则直接对应上述问题：

| 原则 | 解决的问题 |
| --- | --- |
| **编码前思考** | 错误假设、隐藏困惑、缺少权衡 |
| **简洁优先** | 过度复杂、臃肿抽象 |
| **精准修改** | 无关编辑、触碰不应修改的代码 |
| **目标驱动执行** | 缺少验证、只给过程不给成功标准 |

## 四个原则

### 1. 编码前思考

**不要假设，不要隐藏困惑，呈现权衡。**

LLM 很容易默默选择一种理解并直接实现。应显式执行以下行为：

- 明确说明假设；存在不确定性时先提问，不猜测。
- 存在多种合理解释时列出选项，不静默选择。
- 存在更简单的实现路径时说明理由；必要时提出异议，不机械执行。
- 关键事实不清楚时停止执行，指出困惑点并要求澄清。

### 2. 简洁优先

**用最少代码解决问题，不做推测性设计。**

- 不添加要求之外的功能。
- 不为一次性代码创建抽象。
- 不增加未被要求的灵活性或可配置性。
- 不为极低概率场景引入复杂错误处理。
- 如果 50 行代码足以完成目标，不应保留 200 行实现。

检验标准：资深工程师是否会认为实现过于复杂？如果会，继续简化。

### 3. 精准修改

**只修改必须修改的内容，只清理本次改动造成的混乱。**

- 不顺手改进相邻代码、注释或格式。
- 不重构没有损坏的代码。
- 即使个人偏好不同，也优先遵循既有工程风格。
- 发现无关死代码可以报告，但不直接删除。
- 删除本次改动直接造成的无效 import、变量、函数或依赖。
- 不删除既有历史死代码，除非任务明确要求。

检验标准：每一行改动都应能直接追溯到当前任务请求。

### 4. 目标驱动执行

**定义成功标准，循环验证直到达成。**

将指令式任务转换为可验证目标：

| 不要只说 | 应转化为 |
| --- | --- |
| “加上校验” | “先为非法输入写验证或测试，再让它通过” |
| “修复这个 bug” | “先构造能复现 bug 的证据，再修复并验证” |
| “重构 X” | “保证重构前后行为一致，并通过既有验证” |

多步骤任务应先给出简短计划：

```text
1. [步骤] -> 验证：[检查方式]
2. [步骤] -> 验证：[检查方式]
3. [步骤] -> 验证：[检查方式]
```

强成功标准能使执行独立推进；“让它能用”这类弱标准通常只会带来返工和澄清。

## 核心洞察

- LLM 擅长围绕明确目标循环执行，直到达到成功标准。
- 因此不仅要说明“做什么”，还要说明“怎样算完成”。
- 成功标准越具体、越可验证，结果越稳定。

## 生效迹象

协作原则生效后，通常会看到：

- diff 中不必要的改动更少，主要保留任务直接相关的修改。
- 因过度复杂导致的返工更少，首次实现更接近简洁方案。
- 澄清问题发生在实现前，而不是做错以后才补问。
- 提交更干净，没有顺手优化或无关重构。

## 与工程规范协同

本指南约束协作方式与改码行为，不替代工程规范。项目硬性约束以 [工程规则](./ENGINEERING_RULES.md) 和 [DDD 微服务软件工程规范纲要](./standards/00_DDD_MICROSERVICE_SOFTWARE_ENGINEERING_OUTLINE.md) 为准。

建议执行顺序：

1. 先以本文件约束问题澄清、改动范围和验证方式。
2. 再以工程规范约束模块边界、依赖规则、版本基线和质量门禁。
3. 两者出现冲突时，以工程规范的硬性约束为准。

## 项目落地要求

### 对应“编码前思考”

- 涉及版本升级、依赖替换、模块拆分或边界调整时，先确认版本矩阵、影响范围和回归验证方式。
- 遇到“编译通过但边界污染”的实现，不默认接受；应说明问题并给出符合规范的方案。

### 对应“简洁优先”

- 不为单个调用点新增通用抽象。
- 不将运行 Starter、重型依赖或框架能力下沉到共享技术模块。
- 不为未来可能的场景提前铺设未被要求的扩展点。

### 对应“精准修改”

- 非必要不批量重写 Java 源文件，避免引入编码、BOM 或中文注释乱码。
- 只清理本次修改直接产生的无效 import、变量和依赖。
- 发现历史问题时可记录或提醒，但不无边界扩散处理。

### 对应“目标驱动执行”

- Maven 相关改动至少执行与影响范围相符的 `validate`、`compile`、`test` 或 `verify` 验证，具体命令遵循 [Maven 工程规范](./standards/20_MAVEN_ENGINEERING_CONVENTIONS.md)。
- Bug 修复优先提供复现证据、日志、测试或最小验证过程，不只凭阅读代码宣布完成。
- 改动引入新的诊断或静态检查问题时，必须在交付前处理，或明确说明残留风险。

## 交付前检查

- 假设、边界与关键取舍已说明或已澄清。
- 改动范围可追溯到任务目标，未夹带无关重构。
- 已执行适当的构建、测试、编码和诊断验证。
- 结论只陈述已实际验证的事实；未执行项与风险已明确说明。
