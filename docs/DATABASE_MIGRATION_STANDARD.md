# 数据库迁移脚本规范

本规范适用于各服务 `src/main/resources/db/migration/` 下由 Flyway 执行的 SQL 脚本。

## 基本规则

- 使用 Flyway 默认命名：`V{版本号}__{英文描述}.sql`；版本号在单个服务内单调递增且不可复用。
- 文件使用 UTF-8 编码，SQL 关键字使用大写，标识符使用反引号，缩进使用两个空格。
- 每个基线脚本第一行说明所属领域及“仅适用于未执行该基线的新建数据库”。
- 已在任何环境执行的迁移必须保持不可变；结构调整必须新增版本脚本。只有明确确认不存在历史库时才可重建 `V1` 基线。
- 不使用 `IF NOT EXISTS`、`DROP TABLE` 或依赖执行顺序之外的隐式幂等逻辑，避免掩盖环境漂移。

## 表定义

- 一个表对应一个完整的 `CREATE TABLE` 语句；字段、主键、唯一键、普通索引与约束均在该语句中定义。
- 统一显式声明 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`。
- 表、字段、索引和约束均应有能描述业务用途或查询路径的 `COMMENT`。
- 时间字段统一使用 `datetime(3)`；金额使用 `decimal`；布尔开关使用 `tinyint(1)` 或项目既有兼容类型。
- 跨服务关联仅保存对方标识，不创建跨库外键；同服务内是否使用外键由聚合边界和写入模型决定。
- 索引必须对应实际查询、排序、幂等或清理路径；避免重复索引和仅为“可能查询”建立的索引。

## 数据与会话设置

- 字符集由表级定义保证，不在迁移中执行 `SET NAMES`、`SET CHARACTER SET` 等连接级设置。
- 初始化数据仅包含本地启动所需的最小数据，明确标记用途；生产业务数据不得写入基线脚本。
- 密码、密钥、令牌和真实用户隐私数据不得出现在迁移脚本中。

## 提交前验证

1. 使用空数据库执行对应服务的全部迁移，确认 SQL 可执行。
2. 运行该服务的 Flyway 配置与迁移契约测试。
3. 检查迁移文件为 UTF-8、名称符合 Flyway 规则，且没有修改已发布版本。
