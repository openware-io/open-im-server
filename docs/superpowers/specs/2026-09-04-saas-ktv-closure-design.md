# SaaS/KTV 交易闭环整改设计

**目标**：将 SaaS/KTV 从认证可用的骨架收敛为可信的预约、履约、资源、账单和收款闭环，并让 C/B/Admin 三端遵循同一服务端契约。

## 边界

本次只处理 SaaS/KTV 首发闭环，不改变 IM 消息、好友或桌面端业务。现有本地部署脚本和 ACK 配置保持不变。

## 设计

1. **可信身份与上下文**：浏览器只持有 HttpOnly 会话 Cookie；网关从 Redis 会话取签名上下文；上下文选择必须先由 IAM 验证账号与租户/组织/门店关系，失败返回 401/403，不签发空权限 Token。业务服务只从 `TenantContext` 取身份和范围，拒绝请求体覆盖。
2. **C/B 端点隔离**：`/me/*` 只允许当前账号对应会员读取和操作；`/business/*` 只允许带运营权限的上下文访问。预约、订单、资产查询均按租户与会员/门店范围过滤。
3. **资源与履约编排**：订单服务通过资源服务内部命令创建和释放 occupation；开台/点服务人员必须先占用，转台先占新后释放旧，结台/取消/作废幂等释放。预约状态转为 `CONVERTED` 后才能绑定订单。
4. **计时与账单**：暂停保存服务端时间边界并累计 `paused_seconds`；开台固化计价快照，结台只使用快照；服务人员结束时产生唯一 `SERVICE` 明细；账单是唯一应收来源。
5. **收款**：客户端不提交权威应收；服务端按账单快照校验支付腿总额和剩余应收。支付事实、订单实收、Outbox 事件幂等；累计实收等于应收才进入 `COMPLETED`。
6. **交互可靠性**：每次业务提交使用操作级幂等键；网络超时只用同键查询，不生成新交易；CSRF 过期只刷新并重试一次；无上下文、网络失败和权限不足不可使用默认门店或 Mock 数据。

## 验收

- 跨租户/跨门店/非本人预约和订单均返回 403/404，不泄露数据。
- 并发抢同一包厢或服务人员只有一次成功；重复开台、结台、收款不产生第二条事实。
- 暂停 60 秒后恢复或结台，计费少 60 秒；改价不影响已开台会话。
- 篡改应收、过额、部分支付均被服务端拒绝或保持未完成；全额收款回写 `paid_amount` 并发布 `OrderCompleted`。
- C/B/Admin 只使用服务端账单、上下文和支付方式配置；断网不允许以伪数据提交。
